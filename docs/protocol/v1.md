# Blob Royale network protocol v1

* **Status:** Accepted
* **Wire version:** `1.0`
* **Date:** 2026-08-04
* **Deciders:** Project owner
* **Schema dialect:** JSON Schema Draft 2020-12

## Decision

Protocol v1 is a read-only presentation protocol over one HTTP/1.1 listener. It exposes immutable public configuration, liveness, readiness, and a server-pushed WebSocket stream of complete world snapshots. It exposes no lifecycle mutation, player command, identity, or authentication surface.

The canonical state path is `GET /api/v1/snapshots` upgraded to WebSocket with subprotocol `blob-royale.snapshot.v1`. The server samples the latest immutable `WorldSnapshot` at a configured presentation rate independent of the fixed 400 Hz simulation rate. Each connection permits at most one asynchronous write in flight and retains at most one pending snapshot. A newer publication replaces stale pending state. State is never available through HTTP and clients never poll or trigger serialization.

Protocol v1 is safe only on the trust boundary accepted by [`0001-linux-runtime-contract.md`](../architecture/0001-linux-runtime-contract.md): direct loopback use or a private OCI network behind a deployment-managed HTTPS/WSS reverse proxy. It has no authentication. Origin validation limits browser drive-by abuse but does not identify or authorize a caller. Direct exposure to an untrusted network is unsupported.

## Public surface

These four targets are the entire public surface. The router compares the path exactly after HTTP parsing. Query strings, fragments, trailing slashes, percent-encoded path substitutions, and path normalization aliases do not select a route.

| Method | Target | Success | Purpose | Failure statuses |
|---|---|---:|---|---|
| `GET` | `/api/v1/config` | `200` | Return immutable presentation-facing configuration. | `400`, `403`, `405`, `413`, `429`, `431`, `500` |
| `GET` | `/api/v1/health/live` | `200` | Report that the HTTP event loop can parse and answer a request. | `400`, `403`, `405`, `413`, `429`, `431`, `500` |
| `GET` | `/api/v1/health/ready` | `200` | Report that the runtime is active and a complete snapshot is publishable. | `400`, `403`, `405`, `413`, `429`, `431`, `500`, `503` |
| `GET` + WebSocket upgrade | `/api/v1/snapshots` | `101` | Open the server-pushed complete-snapshot stream. | `400`, `403`, `405`, `413`, `426`, `429`, `431`, `500`, `503` |

All other targets return `404`. A known target with any method other than `GET`, including `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, and `OPTIONS`, returns `405` with `Allow: GET`. The implementation MUST NOT infer `HEAD` from `GET` or install framework-generated `OPTIONS` behavior.

The prototype routes `/game-config`, `/game-state`, `/start-sim`, and `/pause-sim` are not aliases and MUST return `404`. No public route starts, pauses, stops, steps, resets, or otherwise mutates the simulation. Process startup is composition-root policy; pause/stop are internal runtime lifecycle operations; process shutdown is owned by `SIGINT`/`SIGTERM` and the external supervisor.

### Route semantics

#### `GET /api/v1/config`

The response validates against `configuration-response.schema.json`. The values are immutable for the process lifetime. A changed configuration requires a new process, which gives clients a new connection and request ID. The response exposes only world geometry, the accepted fixed simulation quantum, presentation cadence, and snapshot bounds. It does not expose spatial-grid shape, thread count, paths, bind address, proxy topology, or other implementation details.

`width_world_units`, `height_world_units`, and `player_radius_world_units` use world units (`wu`). `ticks_per_second` uses ticks per simulated second and is exactly `400`; `fixed_delta_seconds` is exactly `0.0025`. `snapshots_per_second` is an integer in `[1, 60]` and does not change simulation time or physics. `snapshot_player_limit` and `snapshot_frame_max_bytes` are protocol constants, not observations of current occupancy.

The server MUST validate the simulation invariant `width_world_units > 2 × player_radius_world_units` and its height equivalent before accepting traffic. JSON Schema expresses the individual numeric bounds; startup validation owns the cross-field relationship.

#### `GET /api/v1/health/live`

The route returns `200` and `data.status = "alive"` when the server event loop can answer. It deliberately does not inspect simulation progress, snapshot freshness, downstream proxy state, or external reachability. An event loop unable to respond cannot manufacture a useful failure body; the supervisor observes timeout or connection failure.

#### `GET /api/v1/health/ready`

The route returns `200` only when the runtime is in its active state, at least one complete post-tick immutable snapshot exists, the snapshot satisfies protocol limits, and new WebSocket sessions may be accepted. The success body has `status = "ready"` and `snapshot_available = true`.

It returns `503` with `SERVICE.NOT_READY`, `retryable = true`, and `details.retry_after_ms` when initialization is incomplete or coordinated shutdown has begun. An invariant, encoding, or runtime failure is not degraded readiness: it is a hard process failure. The top-level process records the typed failure, stops accepting traffic, closes sessions, and exits nonzero as required by the Linux runtime contract.

#### `GET /api/v1/snapshots`

An ordinary HTTP request to this target returns `426` with `Upgrade: websocket` and `PROTOCOL.UPGRADE_REQUIRED`. A valid upgrade is accepted only while readiness is true and every handshake rule below passes. There is no HTTP snapshot response and no endpoint for fetching the latest state once.

## HTTP contract

### Request parsing

The server accepts HTTP/1.1 requests only. It applies these limits before routing:

| Input | Limit | Failure |
|---|---:|---|
| Request target | 2,048 bytes | `414` transport rejection; close connection |
| Aggregate header section | 16,384 bytes | `431` + `PROTOCOL.HEADER_TOO_LARGE` when representable |
| Header field count | 64 | `431` + `PROTOCOL.HEADER_TOO_LARGE` |
| Request body | 0 bytes on every v1 route | `413` + `PROTOCOL.PAYLOAD_TOO_LARGE` |
| Encoded HTTP JSON response | 65,536 bytes | Treat as internal invariant failure; never truncate |
| Time to receive request headers | 10 seconds | close connection; no response required after timeout |
| Pipelined response queue | 8 responses per HTTP connection | stop reading until the queue drains |
| Requests per keep-alive connection | 100 | send the final response with `Connection: close` |

Every v1 request MUST contain exactly one syntactically valid `Host` field and that authority MUST match the configured allowlist after lowercasing a DNS name and normalizing IPv6 bracket notation. The host and explicit/default port then compare exactly. Direct defaults are `127.0.0.1:8000`, `localhost:8000`, and `[::1]:8000`; a reverse-proxy deployment replaces or extends them with its exact external authority. User-info, suffix/substring matching, and forwarded-host substitution are forbidden. An unmatched `Host` returns `400` with `PROTOCOL.INVALID_REQUEST`. Duplicate singleton headers, obsolete folded headers, invalid field syntax, conflicting message-length headers, or both `Transfer-Encoding` and `Content-Length` produce the same status/code when the parser can safely answer; otherwise the server closes the connection. Request bodies remain forbidden even when framed as zero semantic content by chunked transfer encoding.

The listener performs a bounded raw-byte preflight before HTTP field parsing. Any `CRLF` immediately followed by space or horizontal tab inside the first header section is obsolete line folding and is rejected before the HTTP library can normalize it, regardless of which field is continued. The preflight shares the 16,384-byte header limit and 10-second deadline and consumes only the first complete header section, so already-buffered pipelined requests retain their exact bytes for their own independent preflight.

The service MUST NOT reflect an invalid target, header value, Origin, or payload in an error message or details. It MUST NOT use parser errors as route fallbacks.

### Request IDs

The optional `X-Request-ID` request header is an untrusted correlation hint. It MUST occur at most once and match `^[A-Za-z0-9._:-]{1,64}$`. A duplicate or invalid value returns `400` with `PROTOCOL.INVALID_REQUEST_ID`. A missing value causes the server to generate a collision-resistant opaque identifier that satisfies the same schema.

Every HTTP response repeats the accepted/generated value in `X-Request-ID` and `meta.request_id`. A successful WebSocket upgrade includes `X-Request-ID`; every message on that connection repeats the handshake request ID. Request IDs convey no authority, are not globally ordered, and MUST be encoded as structured log data rather than interpolated into free-form log messages.

### Response envelope and headers

Every JSON response has exactly three top-level members in this order:

1. `data` — the complete typed result on success, otherwise `null`.
2. `error` — `null` on success, otherwise one structured error.
3. `meta` — wire version, schema identity, and request ID.

Partial data plus an error is forbidden. A handler that cannot construct the entire response returns an error envelope or terminates the failing process; it never substitutes empty/default state. All JSON member names use `snake_case`.

JSON responses use UTF-8 without a byte-order mark and send:

```http
Content-Type: application/json; charset=utf-8
Cache-Control: no-store
X-Content-Type-Options: nosniff
X-Request-ID: <validated-or-generated-id>
```

The service emits no `Access-Control-Allow-Origin: *`. The production client is same-origin with the reverse proxy. A separate development origin must appear in an explicit exact origin allowlist and receives its exact origin value plus `Vary: Origin`; credentials remain disabled. An unmatched HTTP `Origin` returns `403` with `PROTOCOL.ORIGIN_REJECTED`.

### HTTP status and error registry

The status code and machine error code are a stable pair. `message` is bounded human context and MUST NOT be parsed. `retryable` tells an automated client whether repeating the same operation can succeed without changing the request. `details` is closed by schema and contains only the named safe fields.

| HTTP status | Error code | Retryable | Required header/details | Meaning |
|---:|---|---|---|---|
| `400` | `PROTOCOL.INVALID_REQUEST` | false | optional safe `reason` | Parsed request violates v1 request rules. |
| `400` | `PROTOCOL.INVALID_REQUEST_ID` | false | none | `X-Request-ID` is duplicate or invalid. |
| `400` | `PROTOCOL.SUBPROTOCOL_REQUIRED` | false | safe `reason` | Snapshot upgrade did not offer `blob-royale.snapshot.v1`. |
| `400` | `PROTOCOL.WEBSOCKET_VERSION_UNSUPPORTED` | false | `Sec-WebSocket-Version: 13`; `expected_websocket_version = "13"` | Upgrade does not offer WebSocket version 13. |
| `403` | `PROTOCOL.ORIGIN_REJECTED` | false | none | Browser origin is absent where required or is not exactly allowed. |
| `404` | `PROTOCOL.ROUTE_NOT_FOUND` | false | none | Exact request target is not public v1. |
| `405` | `PROTOCOL.METHOD_NOT_ALLOWED` | false | `Allow: GET`; `allowed_methods = ["GET"]` | Known route received a forbidden method. |
| `413` | `PROTOCOL.PAYLOAD_TOO_LARGE` | false | `limit = 0` | A v1 request carried a body. |
| `426` | `PROTOCOL.UPGRADE_REQUIRED` | false | `Upgrade: websocket` | Snapshot route was requested without an upgrade. |
| `429` | `PROTOCOL.RATE_LIMITED` | true | `Retry-After`; `retry_after_ms` | Direct-peer request/upgrade budget is exhausted. |
| `429` | `PROTOCOL.CONNECTION_LIMIT_REACHED` | true | `Retry-After`; `retry_after_ms`, `limit` | A global or direct-peer connection bound is reached. |
| `431` | `PROTOCOL.HEADER_TOO_LARGE` | false | `limit = 16384` | Header bytes or field count exceed the parser bound. |
| `500` | `SERVICE.INTERNAL_FAILURE` | false | opaque `reason` only | A response failed after traffic was accepted; process shutdown follows if an invariant broke. |
| `503` | `SERVICE.NOT_READY` | true | `Retry-After`; `retry_after_ms` | Runtime has not published a valid snapshot or shutdown has begun. |

The `414` target-length rejection may occur before a request ID or route exists and therefore need not use the JSON envelope. The server MUST close that connection. Unsupported HTTP versions receive `505` and connection close; malformed bytes that do not yield a safe request context may be closed without a body.

## WebSocket contract

### Upgrade validation

The server accepts an upgrade only when all conditions hold:

1. Method and exact target are `GET /api/v1/snapshots`.
2. HTTP version is 1.1 and the standard `Connection`, `Upgrade`, and `Sec-WebSocket-Key` fields are syntactically valid.
3. `Sec-WebSocket-Version` is `13`.
4. `Sec-WebSocket-Protocol` offers the exact case-sensitive token `blob-royale.snapshot.v1`; the server selects that token.
5. The request-ID rule passes.
6. Readiness is true and connection/rate limits have capacity.
7. Browser-origin policy passes.

For a direct connection whose peer address is loopback, an absent `Origin` is allowed for non-browser test and diagnostic clients. If `Origin` is present, it must be a serialized origin in the configured exact allowlist; wildcard, `null`, user-info, path, query, fragment, suffix, and substring matches are forbidden. For a connection received from the configured reverse-proxy peer set, `Origin` is mandatory and must match the allowlist. Other direct peers are unsupported and rejected.

The `101 Switching Protocols` response selects `Sec-WebSocket-Protocol: blob-royale.snapshot.v1` and returns `X-Request-ID`. Per-message compression is not negotiated in v1. The server does not use cookies, URL tokens, bearer tokens, or query-string credentials.

### Frames and message model

The server sends only unfragmented UTF-8 text data frames. Each frame contains one JSON document validating against `snapshot-message.schema.json` and no leading/trailing non-whitespace bytes. The maximum encoded frame payload is 2,097,152 bytes. The server never emits binary snapshots, deltas, patches, acknowledgements, lifecycle notifications, or in-band error messages.

Clients MUST treat each snapshot as a complete immutable replacement, not merge it into prior state. `tick_sequence` is the committed simulation tick and strictly increases between frames on one connection; the server suppresses duplicate ticks. `message_sequence` starts at `1` after each upgrade and increments by exactly one per delivered snapshot. It measures transport messages, not simulation work. A reconnect creates a new request ID and resets `message_sequence`; `tick_sequence` continues with the process.

The `players` array is ordered by ascending `entity_id`, contains no duplicate IDs, and represents one coherent tick. Object member order is deterministic:

* Envelope: `data`, `error`, `meta`.
* Snapshot data: `tick_sequence`, `players`.
* Player: `entity_id`, `position`, `velocity`, `acceleration`.
* Vector: `x`, `y`.
* Snapshot metadata: `protocol_version`, `schema_id`, `request_id`, `message_sequence`, `sent_at_utc`.

JSON object order is not semantically significant to general decoders, but `blob_protocol` MUST encode in this order so golden bytes, logs, and repeated tests are deterministic. Numbers are JSON numbers. IDs and sequences never exceed JavaScript's exact integer ceiling `9,007,199,254,740,991`. Every physical component is a finite binary64 value encoded with a round-trip-safe decimal representation. `-0` is forbidden because the deterministic simulation contract canonicalizes signed zero before publication.

Units follow [`0003-deterministic-simulation-contract.md`](../architecture/0003-deterministic-simulation-contract.md): position uses `wu`, velocity uses `wu/s`, acceleration uses `wu/s²`, and one tick represents exactly `1/400 s`. The network performs no interpolation, prediction, collision calculation, or unit conversion.

### Presentation cadence and stale replacement

The configured `snapshots_per_second` defines presentation slots on `steady_clock`; it does not schedule or pace simulation ticks. At each slot a session reads the newest retained immutable publication:

1. If the tick is not newer than the last delivered or pending tick, do nothing.
2. If a write is active, retain one immutable snapshot reference as pending; replace it only with a newer tick and never append a second pending item.
3. If no write is active, retain the latest snapshot as pending and request one turn from the event-loop-confined global encoding/egress budget. Admission reserves the full 2,097,152-byte protocol maximum before encoding begins.
4. If admission is denied, keep the session open and leave only its latest pending reference. Denied sessions occupy at most one entry in a fixed 32-session FIFO; a later presentation slot retries the queue head. Closing or control-blocked sessions leave the FIFO, and capacity release never wakes work outside presentation cadence.
5. Only after admission, promote pending state to the active write, assign the next `message_sequence`, serialize once, and commit the actual encoded byte count. Unused worst-case reservation bytes are refunded.
6. On write completion, release the written buffer and its committed global payload bytes. Do not start another data write until a later presentation slot.

This yields at most the configured presentation rate, at most one write buffer plus one immutable pending reference per connection, and latest-state behavior under delay. Slow clients lose intermediate presentation snapshots by design; they never slow or mutate the simulation. Clients detect skipped simulation ticks through `tick_sequence` and skipped transport delivery through reconnect/message sequence, but no replay is available.

Presentation deadlines advance from the prior scheduled deadline rather than `now`, so handler lateness does not permanently drift cadence. Missed slots coalesce into one latest-snapshot opportunity. A session MUST NOT burst multiple frames to catch up.

### Client frames, keepalive, and close codes

Application data is one-way. Any client text or binary data frame, including the prototype acceleration-shaped message, closes the connection with code `1008` and reason `client_data_forbidden`. Payload interpretation never occurs.

The inbound application-message limit is 1,024 bytes so a peer cannot force unbounded buffering before policy rejection. An oversized data message closes with `1009` and reason `client_message_too_large`. Standard close, ping, and pong control frames are allowed. A direct peer may send at most five control frames in a burst and one control frame per second thereafter; excess closes with `1008` and reason `control_rate_exceeded`.

The server sends a ping after 15 seconds without receiving any frame and requires a pong within 10 seconds. It closes an unresponsive peer with `1001` and reason `peer_timeout`. A data write that does not complete within 5 seconds is terminated with close intent `1013` and reason `slow_consumer`; the pending reference is discarded. Because a WebSocket close frame cannot be safely queued behind the same stalled write, the server cancels and closes the socket. The peer may therefore observe an abnormal transport close instead of receiving the intended `1013` frame. Other server-initiated closes use the listed close frame when the transport remains writable.

| Code | Stable reason | Initiator | Meaning |
|---:|---|---|---|
| `1000` | `normal` | either | Normal client close. |
| `1001` | `server_shutdown` | server | Coordinated process shutdown; client may reconnect after deployment policy permits. |
| `1001` | `peer_timeout` | server | Keepalive deadline expired. |
| `1002` | `protocol_error` | server | Invalid WebSocket framing or control semantics. |
| `1007` | `invalid_utf8` | server | A client text frame is not valid UTF-8. |
| `1008` | `client_data_forbidden` | server | Client sent an application data frame. |
| `1008` | `control_rate_exceeded` | server | Client exceeded control-frame rate. |
| `1009` | `client_message_too_large` | server | Client data message exceeded 1,024 bytes. |
| `1011` | `internal_failure` | server | Snapshot encoding or session invariant failed; no partial/error frame follows. |
| `1013` | `slow_consumer` | server | One write exceeded 5 seconds. |
| `1013` | `service_not_ready` | server | Readiness became false before coordinated shutdown completed. |

Close reasons are bounded ASCII diagnostics, not error envelopes. A client uses the numeric code for policy. On `1011`, a protocol/snapshot invariant failure also transitions readiness false and invokes hard process failure rather than silently skipping malformed state.

## Resource and rate policy

Limits apply at the application listener even behind a proxy. They protect origin availability, but they do not replace stricter edge limits.

| Resource | Bound | Action at bound |
|---|---:|---|
| Concurrent accepted TCP connections | 128 global | Refuse/close newest; return `429` when HTTP context exists. |
| Concurrent WebSocket sessions | 32 global | Reject upgrade with `429`. |
| Concurrent WebSocket sessions per socket-derived accounting principal | 8 | Reject upgrade with `429`. |
| Retained socket-derived accounting principals | 128 | Prune expired entries, then evict the oldest inactive entry with lexical tie-break; deny a new identity if every entry is active. |
| HTTP requests per socket-derived accounting principal | Token bucket: capacity 20, refill 2/second | `429`; include whole-second `Retry-After`. |
| WebSocket upgrade attempts per socket-derived accounting principal | Token bucket: capacity 4, refill 0.2/second | `429`; include whole-second `Retry-After`. |
| Active WebSocket data writes per session | 1 | Keep/replace one pending immutable snapshot. |
| Pending snapshots per session | 1 | Replace only with latest tick. |
| Active encoded snapshot payload bytes | 16,777,216 global | Deny the presentation slot before encoding; retain only latest pending state. |
| Encoded snapshot byte-rate bucket | 16,777,216-byte capacity; 67,108,864 bytes/second refill | Queue one fair retry turn per session; charge actual encoded bytes. |
| Outgoing snapshot payload | 2,097,152 bytes | Treat as internal invariant failure; no truncation. |
| Players in a snapshot | 4,096 | Reject configuration/startup; no truncated array. |

Each syntactically parsed request consumes a request token before route selection, including an oversized target that then closes without an envelope. Each upgrade attempt consumes both one HTTP request token and one upgrade token. Buckets use `steady_clock`, do not go negative, and disappear after the direct peer has no connections and has been idle for 10 minutes. All IPv4 addresses in `127.0.0.0/8` and IPv6 `::1` form one loopback accounting principal; every other supported peer uses its canonical socket address. The bounded identity ledger deterministically evicts only inactive entries. Limits count this socket-derived principal only. The application MUST ignore `Forwarded`, `X-Forwarded-For`, `X-Real-IP`, and similar caller-supplied identity fields for application rate accounting.

Global egress accounting measures logical uncompressed JSON payload `size()`, not allocator capacity, transient encoder DOM memory, WebSocket framing, TLS, kernel socket buffers, or total process RSS. The one event loop permits only one synchronous encoder invocation at a time; the active byte cap additionally bounds aggregate completed payloads retained by asynchronous writes. There is no worker executor, unbounded work queue, replay queue, or alternate snapshot delivery path.

Behind a reverse proxy, every external caller may appear as the proxy peer. The deployment MUST therefore enforce client-aware connection and request limits at the proxy, while sizing the origin's configured proxy-peer allowance deliberately. Protocol v1 does not define trusted forwarded-client identity.

## Reverse proxy and deployment boundary

Direct/default execution binds `127.0.0.1:8000`; IPv6 loopback may be enabled explicitly as `[::1]:8000`. Non-loopback binding is an explicit deployment change and is supported only on a private OCI network whose ingress is a managed reverse proxy. The application has one listener for HTTP and WebSocket traffic and does not terminate TLS.

The reverse proxy deployment MUST:

* Terminate HTTPS/WSS with deployment-approved certificates and current secure TLS policy.
* Redirect or reject plaintext external HTTP before it reaches the private listener.
* Forward WebSocket upgrade headers and the exact request target without rewriting protocol versions.
* Preserve the browser `Origin` and set an exact external `Host` accepted by deployment configuration.
* Disable response buffering for the snapshot stream and set idle timeouts longer than the protocol keepalive window.
* Apply external client-aware connection, header, request, and upgrade-rate bounds.
* Strip untrusted forwarding/request-ID headers or pass them only after applying this contract's validation.
* Keep the origin listener unreachable from the public network.

The application does not credit proxy authentication, a firewall, TLS, or rate limits unless deployment artifacts configure them. `X-Forwarded-Proto: https` does not make a directly reachable plaintext listener safe. If the service becomes shared or internet-facing, an accepted protocol amendment must define caller identity, authorization, confidentiality expectations, proxy trust configuration, security telemetry, and player ownership before exposure.

## Trust boundaries and threat cartography

The lenses are trust-boundary analysis, STRIDE for the network decomposition, and capability discipline for preventing a read-only server from acquiring simulation authority.

### Assets and principals

| Asset | Protected property | Principal that owns it |
|---|---|---|
| Mutable simulation world | Integrity and deterministic tick order | `SimulationRuntime` writer thread only |
| Immutable published snapshot | Coherence, bounded serialization, monotonic identity | `SnapshotPublication` and `blob_protocol` |
| Process resources | Bounded sockets, buffers, CPU, and shutdown time | `GameServer`/external supervisor |
| Public configuration | Accurate units and rendering bounds | Immutable application configuration |
| Request correlation | Log-safe opaque linkage, not identity | HTTP/WebSocket boundary |

There are no v1 account records, credentials, player commands, private game sessions, or durable user data. Snapshot confidentiality is not protected from any caller that can reach the private listener. That is an explicit limitation, not evidence that the listener is safe to publish.

### Boundaries

| Boundary | Crossing | Validation/control | Assumption not granted |
|---|---|---|---|
| Untrusted HTTP peer → `GameApiRouter` | Method, target, headers, body, request cadence | Parser bounds, exact routes/methods, request-ID/origin checks, rate buckets | Network reachability does not grant lifecycle or simulation capability. |
| Untrusted WebSocket peer → `SnapshotWebSocketSession` | Upgrade fields and control/data frames | Exact path/subprotocol/origin, frame bounds, one-way policy, keepalive/rate limits | Origin is not authentication; client frames are not commands. |
| Runtime publication → protocol encoder | `shared_ptr<const WorldSnapshot>` | Immutable reference, tick/order/finite/range checks, schema/size conformance | Encoder cannot access `GameSimulation` or runtime lifecycle methods. |
| Protocol encoder → browser client | Complete JSON snapshots | Closed schemas, deterministic fields/order, frame limit | Client still validates untrusted network data before rendering. |
| Public TLS proxy → private application listener | Decrypted HTTP/WebSocket stream | Private network, configured proxy peers, preserved Origin/Host, origin limits | Forwarding headers are not client identity in v1. |
| Supervisor/signals → application lifecycle | Start/restart/stop authority | OCI policy, `SIGINT`/`SIGTERM`, ordered RAII shutdown | No network request can invoke this authority. |

The server receives only `const SnapshotPublication&` and immutable server configuration as described by [`0002-simulation-architecture.md`](../architecture/0002-simulation-architecture.md). It MUST NOT receive `GameSimulation&`, `SimulationRuntime&`, a lifecycle callback, a mutable snapshot pointer, or a singleton accessor. This capability boundary makes the absence of start/pause routes structural rather than conventional.

### Abuse cases and controls

| Attacker action | Consequence sought | v1 control | Residual risk |
|---|---|---|---|
| A web page opens many cross-site WebSockets to loopback. | Drive-by CPU/socket exhaustion and snapshot disclosure. | Exact Origin allowlist, no wildcard CORS, upgrade bucket, connection caps. | A locally allowed or compromised origin can still read all snapshots; Origin is not identity. |
| A slow peer stops reading snapshots. | Unbounded queued state and memory exhaustion. | One write plus one replaceable pending reference; 5-second write deadline; `1013`. | Up to the fixed per-session buffer cost remains across 32 sessions. |
| A peer floods HTTP, upgrades, or ping frames. | Event-loop and log exhaustion. | Parser/time bounds, separate token buckets, control-frame rate, bounded connections. | A distributed attack or proxy-collapsed source needs edge enforcement. |
| A peer sends huge or malformed headers/bodies/frames. | Allocation pressure or parser ambiguity. | Byte/count/time limits, body forbidden, 1,024-byte inbound frame limit, fail closed. | Bugs in Boost.Beast or allocator behavior remain dependency risks. |
| A caller supplies control characters as a request ID. | Log injection and correlation spoofing. | Single bounded ASCII request-ID grammar and structured logging. | Valid IDs are caller-chosen and therefore never establish identity. |
| A client sends acceleration or lifecycle-shaped JSON. | Mutate the simulation through a confused deputy. | No decoder or command capability; all application frames close `1008`. | A future command version must add identity, ownership, tick ordering, and authorization together. |
| An operator publishes the plaintext listener. | Unauthenticated snapshot disclosure and resource abuse. | Loopback default, private-network-only contract, readiness documentation. | There is no in-process protection against operator misexposure; v1 is not internet-safe. |
| A direct peer spoofs `X-Forwarded-For`. | Evade rate limits or impersonate a caller. | Ignore forwarding identity for application limits. | Proxy deployments need their own trusted-client accounting. |

### Explicitly out of scope

* Authentication, sessions, accounts, authorization, player identity, and player ownership.
* Player commands, acceleration changes, input sequencing, reconciliation, rollback, and acknowledgements.
* Confidential snapshots or tenant/game isolation.
* Internet DDoS resistance, WAF behavior, proxy selection, certificate issuance, and client-IP forwarding trust.
* Snapshot replay, resume tokens, history, deltas, compression, binary encoding, and HTTP state retrieval.
* Metrics/admin/debug routes, runtime configuration reload, process lifecycle routes, matchmaking, and persistence.

These exclusions do not declare the omitted threats harmless. They constrain supported deployment to trusted loopback/private boundaries. Adding any player command before authentication/ownership is defined would turn the server into a confused deputy and requires a new accepted protocol surface.

## Field dictionary and invariants

| Field | Type/bound | Unit/meaning | Ordering/invariant |
|---|---|---|---|
| `protocol_version` | constant string `"1.0"` | Wire contract version | Present in every envelope. |
| `schema_id` | bounded string | Exact message schema identity | One constant per envelope schema. |
| `request_id` | 1–64 safe ASCII chars | HTTP request / WebSocket connection correlation | Stable for one upgraded connection; no authority. |
| `message_sequence` | integer `[1, 2^53-1]` | Delivered messages on one connection | Starts at 1; increments exactly once. |
| `sent_at_utc` | RFC 3339 date-time ending `Z` | Message-construction wall time in UTC | Observability only; never simulation input. |
| `tick_sequence` | integer `[1, 2^53-1]` | Complete committed simulation ticks | Strictly increases per connection. |
| `players` | array, 0–4,096 items | Complete player population | Ascending unique `entity_id`; never partial. |
| `entity_id` | integer `[1, 2^53-1]` | Stable simulation identity | Unique within snapshot; exact equality. |
| `position.x/y` | finite number within schema bound | `wu` | Committed center; server also enforces world/radius bounds. |
| `velocity.x/y` | finite number within schema bound | `wu/s` | Complete post-tick velocity. |
| `acceleration.x/y` | finite number within schema bound | `wu/s²` | Stored acceleration; v1 cannot change it. |
| `snapshots_per_second` | integer `[1,60]` | Presentation slots per wall-clock second | Independent of 400 Hz physics. |

Schema validation alone cannot prove ascending IDs, uniqueness by one property, cross-document world bounds, nonnegative signed zero, strict tick monotonicity, exact encoded byte size, or the data/error exclusivity over transport status. C++ conformance tests MUST cover these normative invariants in addition to validating schemas.

## Alternatives considered

### HTTP polling for current state

Rejected. It duplicates the state surface, lets callers choose serialization rate, adds request/parser overhead to every frame, and makes slow-client pressure harder to coalesce. Liveness, readiness, and immutable configuration remain HTTP because they are small request/response resources; world state has exactly one transport.

### Client-triggered WebSocket snapshots

Rejected. The prototype's one-frame-in/one-snapshot-out behavior lets an unauthenticated peer drive serialization and disguises polling as a persistent connection. Server-push cadence owns the cost and makes inbound application data unequivocally invalid.

### Push every simulation tick

Rejected. A 400 Hz network cadence couples rendering cost to physics and amplifies slow-client pressure. Presentation samples immutable publications at `1–60 Hz`; simulation correctness remains independent of wall-clock delivery.

### Queue every snapshot for reliable delivery

Rejected. Presentation state becomes obsolete as soon as a newer complete snapshot exists. Reliable history would create unbounded memory or simulation backpressure. One replaceable pending reference makes the loss policy explicit.

### Binary deltas or compressed JSON

Rejected for v1. Complete JSON snapshots and Draft 2020-12 schemas maximize inspectability and provide one code-generation/test source while the game remains small. Deltas require base-version recovery; compression adds CPU/memory and cross-origin compression concerns. Either is a new negotiated protocol extension, not an invisible optimization.

### Add authentication before player semantics

Rejected for v1, not rejected permanently. There is no player/session ownership model for an identity to authorize. A token parser without an authorization object would add operational friction while leaving the core decision undefined. The consequence is strict: v1 remains local/private and cannot be presented as an authenticated internet service.

## Consequences

* **Positive:** One read-only state path prevents route drift and makes server cost independent of client polling behavior.
* **Positive:** Immutable complete snapshots preserve the single-writer boundary and never expose a partially completed tick.
* **Positive:** Closed, bounded schemas give C++ tests and generated frontend types one machine-readable source.
* **Positive:** Stable envelopes, request IDs, schema IDs, and error codes make failures distinguishable from empty state.
* **Positive:** Exact origin, parser, connection, cadence, and backpressure rules make the supported local/private threat boundary testable.
* **Negative:** Slow clients skip intermediate ticks, and reconnecting clients cannot replay history.
* **Mitigation:** Snapshots are presentation state; tick/message sequences expose loss. Replay requires a separately bounded history protocol.
* **Negative:** Full JSON snapshots use more bandwidth than deltas or binary frames.
* **Mitigation:** Measure the accepted 4,096-player/2 MiB boundary on native Linux before adding another encoding via `@extension-point snapshot_encoding`.
* **Negative:** Exact closed schemas require a new version even for additive wire fields.
* **Mitigation:** This keeps generated types and conformance behavior unambiguous; version negotiation already has path and subprotocol boundaries.
* **Negative:** No authentication means any peer with listener reach can read snapshots and consume bounded resources.
* **Mitigation:** Default loopback/private ingress is part of the contract. Shared/public deployment is blocked on an authentication/authorization amendment.
* **Operational:** Proxy timeouts, Origin/Host allowlists, and edge limits must agree with this document; unknown deployment controls receive no security credit.
* **Reversibility:** A v2 route/subprotocol can add commands, identity, deltas, or another encoding without mutating v1 semantics or the simulation/publication ownership model.

## Non-loopback and shared-deployment readiness checklist

Acceptance fixes the protocol-v1 wire and trust-boundary contract. It does not claim that the unknown
deployment, reverse-proxy, or operator facts are ready. Before any non-loopback or shared deployment,
the owner and operator must answer each applicable item with evidence, not inference:

* [ ] The four exact routes are sufficient for the v1 browser and deployment probes; no lifecycle, admin, debug, or HTTP state route is needed.
* [ ] `blob_server` can be constructed with only immutable server configuration and `const SnapshotPublication&`; it receives no mutation/lifecycle capability.
* [ ] The presentation default and `[1,60]` range are operationally acceptable independently of the fixed 400 Hz simulation rate.
* [ ] A 4,096-player, 2 MiB complete-frame ceiling fits the intended first deployment and fails startup/encoding visibly when exceeded.
* [ ] One active write plus one replaceable pending reference is implemented per connection; no queue, replay, or catch-up burst remains.
* [ ] Same-origin production delivery and the exact development/proxy Origin allowlist are known before non-loopback binding.
* [ ] The reverse proxy preserves Upgrade/Origin, disables stream buffering, uses timeouts longer than 25 seconds, and rate-limits actual external clients.
* [ ] The application ignores forwarding headers for identity/rate decisions and its private listener is unreachable from an untrusted network.
* [ ] Every success/error/example validates against local Draft 2020-12 schemas with no network resolution, and negative fixtures exercise non-schema invariants.
* [ ] HTTP/WS parser, connection, message, cadence, control-frame, and write-deadline bounds have deterministic integration tests.
* [ ] Logs correlate validated request IDs without reflecting untrusted payloads, origins, or headers and without treating IDs as caller identity.
* [ ] Product/deployment documentation says plainly that v1 has neither authentication nor confidential snapshots and is not internet-safe.
* [ ] A future command proposal versions the protocol and defines authentication, player ownership, authorization, tick addressing, ordering, conflicts, and disconnect behavior together.
