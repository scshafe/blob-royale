# Blob Royale network protocol v3

* **Status:** Accepted
* **Wire version:** `3.0`
* **Date:** 2026-09-10
* **Release state:** In development; not independently deployable until the dynamic-arena plan's final gate
* **Deciders:** Project owner
* **Schema dialect:** JSON Schema Draft 2020-12

## Decision

Protocol v3 replaces the active v2 session surface with `GET /api/v3/lobbies` for
discovery and `GET /api/v3/lobbies/<lobby_id>/session` for joining a room, upgraded with
`blob-royale.session.v3`. Closing the socket leaves the room. There is no `/api/v3/session`
alias. Terrain is published once in welcome, shared by every mode and browser world layer.

Every v1 route, schema, limit, and behavior stays unchanged: `/api/v1/config`,
`/api/v1/health/live`, `/api/v1/health/ready`, and `/api/v1/snapshots` remain served.
The closed v1 error registry does not acquire v3 errors. This document carries forward the
implemented v2.5 session behavior except for the explicit v3 changes below. Historical v2
schemas/examples remain validated, but there is only one active session encoder/decoder.
References below to features introduced in 2.3/2.4 describe their origin, not a second active
major or an additional v3 version. [Historical v2](v2.md) is evidence, not a compatibility path.

A session receives one `welcome` message and then `snapshot` frames at presentation cadence. A
snapshot is a complete immutable tick: every published entity in ascending `entity_id` order,
carrying the components it holds keyed by component kind, plus a generic `match` section. Entity-
shaped state is published only as components and is never duplicated in `match`; the royale safe
zone is the `zone` component of the zone entity, exactly as
[`0005-royale-mode.md`](../architecture/0005-royale-mode.md) § "Match section fields" requires.

A session may send command envelopes `{kind, payload}`, one closed schema per kind, `set_thrust`
first. **A command names no entity.** The server stamps the sending session's own body, so entity
spoofing is not a check that can be forgotten — it is a shape that does not exist on the wire.

Protocol v3 has no in-application authentication. Its trust boundary is the tailnet: reachability of
`https://cole-ubuntu-pc.colobus-stargazer.ts.net:8444` is the whole authorization decision, and
`tailscale serve` is the component that makes it. Anything that can reach the origin listener can
join, steer a blob, and read every other player's position and display name. That is an accepted
boundary for a single-operator host on a private tailnet and is not safe anywhere else.

and would also be wrong. It is impossible because the v1 envelope pins `meta.protocol_version` to

per version.

## Public surface

v3 serves two target families: the directory and the canonical room session. The router compares the path exactly after HTTP parsing; query strings, fragments,
trailing slashes, percent-encoded substitutions, and normalization aliases do not select any of
them. `<lobby_id>` is v3's one parametric segment, and § "The lobby directory" gives its grammar.

| Method | Target | Success | Purpose | Failure statuses |
|---|---|---:|---|---|
| `GET` | `/api/v3/lobbies` | `200` | Read the directory: every room's mode, map, phase, seat census, session count, and health. | `400`, `405`, `413`, `429`, `431`, `500` |
| `GET` + WebSocket upgrade | `/api/v3/lobbies/<lobby_id>/session` | `101` | Join room `<lobby_id>`. | `400`, `403`, `404`, `405`, `409`, `413`, `426`, `429`, `431`, `500`, `503` |

An ordinary HTTP request to a session target returns `426` with `Upgrade: websocket` and
`PROTOCOL.UPGRADE_REQUIRED`. Any method other than `GET` returns `405` with `Allow: GET`. There is
no v3 configuration route, no v3 health route, and no HTTP way to write match state: the directory
is v3's one HTTP read, and it is read-only. A client that wants configuration still calls
`GET /api/v1/config`, and a probe still calls the v1 health routes, which read room 1. Adding a
second config route would give the deployment two sources for one set of numbers.

No session target is a lifecycle route. A session cannot start, pause, stop, step, reset, or
reconfigure a simulation, cannot select the mode or map, cannot seat a bot except through the lobby
commands, and cannot name an entity. The mode, the map, the room count, and each room's initial
seats are composition-root configuration fixed for the process lifetime (`0005-royale-mode.md`
§ "Mode configuration", `0006-lobbies-as-rooms.md`), which is also why a session's advertised
command set cannot change mid-connection.

### Retired v2 routes and error-envelope precedence

The recognized retired paths are exactly `/api/v2/session`, `/api/v2/lobbies`, and
`/api/v2/lobbies/<lobby_id>/session` with the same `[1-9][0-9]{0,2}` id grammar.
Recognition is independent of room existence: room 999 is a retired route even on a one-room
server. These paths return `426 PROTOCOL.SESSION_VERSION_UPGRADE_REQUIRED`, non-retryable,
with fixed `details.required_protocol_version: "3.0"` and guidance naming the canonical v3
route and subprotocol. The response never echoes the raw request target. No v2 socket opens.

Retirement runs after existing global identity, HTTP/request-budget, request-ID, framing,
Host, and supplied-Origin checks, but before method checks, WebSocket handshake validation,
readiness/fullness, upgrade-token consumption, or WebSocket/controller/session allocation.
Thus a valid retired POST or a malformed WebSocket attempt receives the same retirement
response. A rejected supplied Origin or invalid Host still receives its established error
first; an absent Origin can reach retirement because active-upgrade Origin requirements
run later. A retired request consumes normal HTTP accounting, never an upgrade token.

All representable errors for parsed targets beginning `/api/v2/` or `/api/v3/` use the
single current v3 session error envelope, including early security errors and malformed old
aliases. Only grammar-valid retired paths receive the new retirement code. Query strings,
leading-zero ids, percent encodings, trailing slashes, and other non-routes retain ordinary
route errors. Failures without a parsed target retain the existing generic transport fallback.
This is an intentional error-envelope migration, not a general v2 encoder or v1 registry change.

Active v3 routes retain ordinary semantics: missing WebSocket upgrade is
`426 PROTOCOL.UPGRADE_REQUIRED`; an old-only session token is
`400 PROTOCOL.SUBPROTOCOL_REQUIRED`; a mixed offer selects only the v3 token. An
`Upgrade: websocket` header is merely the transport hint, not an application-major selector.
The retirement response sends this fixed header and a `Connection: Upgrade` option (also
`close` when the request is not persistent), as required by
[RFC 9110 §§7.8 and 15.5.22](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.22).
It remains an ordinary HTTP failure, never a `101` or permission to send upgraded data.

### The lobby directory

`GET /api/v3/lobbies` answers `200` with one document conforming to
`lobby-directory-message.schema.json`. `data.lobbies` lists every room the process runs, in
`lobby_id` order, numbered `1..N` with no gaps: `N` is the configured `[lobbies] count`, at most 8.
Each listing is read from two places that are never one. The room's latest committed snapshot gives
`mode`, `map`, `phase`, `phase_started_tick`, `tick_sequence`, `seat_count`, `filled_seat_count`,
and `npc_seat_count`, exactly as that snapshot's `match` section would; the server's own admission
ledger gives `session_count`, the sessions currently admitted to the room; and `seat_count_maximum`
is the room's map's spawn-marker count, the same number its welcomes publish. `healthy` is whether
a join would not answer `503` right now: the room's runtime is running and has published at least
one snapshot. A room that has committed nothing lists its initial world at `tick_sequence` `0` --
the seats it was configured with, nobody in them, its phase `lobby` -- with `healthy` `false`.

The directory is a point-in-time read and not a subscription, and its two sources are read at
different instants, so it is advice rather than a promise: admission is the decision, and a client
that chose a room from the directory can still receive `409` from it. Its metadata is the HTTP
envelope's three members -- `protocol_version`, `schema_id`, `request_id` -- and never
`message_sequence` or `sent_at_utc`, because it is a response and not a frame. It is served under
the ordinary per-principal HTTP bucket of v1 § "Resource and rate policy". Nothing in it is
confidential: who is in which room is the same fact every session's snapshots already publish.

`<lobby_id>` in `/api/v3/lobbies/<lobby_id>/session` MUST match `[1-9][0-9]{0,2}`, and the
segments on either side of it MUST match exactly. A leading zero, a fourth digit, a trailing slash,
a percent-encoded digit, a query string, an empty segment, or any other string in that position
selects nothing and answers `404 LOBBY.NOT_FOUND`, and so does a well-formed id above `N`. The
grammar is wider than the directory bound on purpose: a client that names room `12` on an
eight-room server gets the same `404` as one that names room `999`, and the router never has to
know how many rooms exist to refuse a malformed segment. Room one uses only
`/api/v3/lobbies/1/session`; `/api/v3/session` is not a route.

**Admission** runs after every upgrade rule of § "Upgrade validation" and before the `101` is
written. A room whose runtime has failed or has not yet published answers `503 LOBBY.UNAVAILABLE`;
a room whose admitted session count already equals its `seat_count` answers `409 LOBBY.FULL`; a
room with no lobby publishes an empty roster and is never full this way, because it has no seats
for anybody to be refused from. The
count admission compares against is the room's live `seat_count`, which anyone in that lobby may
change with `set_seat_count`: an occupant who shrinks the lobby lowers what admission will accept,
which is no more authority than the lobby commands already grant. Both answers carry
`details.lobby_id` naming the room. A session counts itself into its room when it is admitted and
out of it when it closes, on every close path.

**The one join the tick can still refuse is the race for the last seat.** Two sessions admitted
against one remaining seat both pass admission, and the tick seats whichever join ranks earlier in
the batch. The other observes a roster its join could not change -- no empty seat, and no declared
bot's seat to take while the room is in `lobby` or `countdown` -- with none of the seats its own,
and the server closes it `1013 lobby_full`. That session has received no welcome and no snapshot:
the welcome names the session's first body, and a session with no seat never gets one. The same
close answers a session admitted to a room every seat of which was already held by the time its
join reached the tick, whatever the room's phase.

### Error registry additions

| HTTP status | Error code | Retryable | Required header/details | Meaning |
|---:|---|---|---|---|
| `426` | `PROTOCOL.SESSION_VERSION_UPGRADE_REQUIRED` | false | `details.required_protocol_version: "3.0"` | A recognized retired v2 route; reconnect using the fixed v3 guidance. |
| `400` | `PROTOCOL.INVALID_FORWARDED_CLIENT` | false | `forwarded_client_reason` | A proxy-forwarded connection did not present exactly one canonical `X-Forwarded-For` address. |
| `404` | `LOBBY.NOT_FOUND` | false | none | The target is not exactly `/api/v3/lobbies/<lobby_id>/session` with `<lobby_id>` in `[1-9][0-9]{0,2}`, or names a room above the configured count. Added in 2.4. |
| `409` | `LOBBY.FULL` | true | `details.lobby_id` | The room's admitted session count already equals its `seat_count`. Read the directory and choose another room, or retry once somebody leaves. Added in 2.4. |
| `503` | `LOBBY.UNAVAILABLE` | true | `details.lobby_id` | The room's runtime has failed or has not published its first snapshot. Another room may be serving; the directory says which. Added in 2.4. |

`forwarded_client_reason` is a closed enum — `absent`, `multiple_values`, `not_canonical` — and not
free text, so no byte of an attacker-supplied forwarding header can reach a response body or a log
line. `PROTOCOL.SUBPROTOCOL_REQUIRED` gains one meaning without gaining a row: it is also the answer
when an upgrade offers a subprotocol token that belongs to a different route's version.

`LOBBY.NOT_FOUND` carries no `lobby_id`, because the request named no room the server recognizes
and echoing the segment would put a client-chosen byte in a response body. `LOBBY.FULL` and
`LOBBY.UNAVAILABLE` name the room in `details.lobby_id`, an integer the router validated before
admission ran, so a client can correlate the refusal with the listing it read.

### Upgrade validation deltas

Rule 4 becomes: `Sec-WebSocket-Protocol` MUST offer the exact case-sensitive token
`blob-royale.session.v3`, and the server selects that token. **Route and subprotocol are validated
as a pair.** The server MUST NOT select `blob-royale.snapshot.v1` on `/api/v3/lobbies/1/session`, MUST NOT
select `blob-royale.session.v3` on `/api/v1/snapshots`, and MUST reject with `400` and
`PROTOCOL.SUBPROTOCOL_REQUIRED` when the offer list contains no token matching the requested route,
even when it contains a token matching the other route. An offer list containing both tokens on
either route selects only that route's token. A protocol that let a client choose which version's
semantics a route runs would let it choose the weaker one.

Rule 7, browser-origin policy, gains a precedence rule that v1 did not need. v1 allows an absent
`Origin` for a direct loopback peer and requires `Origin` from a configured reverse-proxy peer.
**When an address appears in `trusted_proxy_addresses`, its connections are proxy-forwarded and the
direct-peer relaxation does not apply to them.** On the accepted tailnet deployment the proxy is
`tailscale serve` on the host's own loopback address
([`../operations/tailnet.md`](../operations/tailnet.md) § "Limits behind the proxy"), so once
loopback is configured as a trusted proxy there is no direct loopback peer at all: every loopback
connection MUST present a valid `Origin` and a valid `X-Forwarded-For`. Without this precedence rule
the two v1 sentences would overlap on exactly the deployed configuration, and the overlap resolves
in favor of the weaker rule.

Beyond that, a v3 upgrade is admitted under the same host allowlist, request-ID grammar, origin
allowlist, readiness gate, connection caps, and token buckets as a v1 upgrade. It consumes one HTTP
request token and one upgrade token from the same buckets.

The `101` response selects `Sec-WebSocket-Protocol: blob-royale.session.v3` and returns
`X-Request-ID`. Per-message compression is not negotiated. The server uses no cookies, URL tokens,
bearer tokens, or query-string credentials, and v3 introduces none: **there is no resume token, no
session token, and no rejoin credential anywhere in this protocol**, so there is no long-lived
bearer secret for a client, a log, a proxy, or a browser history entry to leak.

## Identity

The tailnet authenticates. The application does not, and MUST NOT be described as if it does. What
the application does is derive one **accounting principal** and one **display name** per connection,
before any route runs, by a total function of the socket peer address and two header fields.

### Principal derivation

1. If the socket peer address is a member of the configured `trusted_proxy_addresses` set, the
   connection is **proxy-forwarded**. Otherwise it is **direct**. This classification is computed
   once, from the socket, and is the only place proxy trust is decided.
2. A proxy-forwarded connection MUST carry exactly one `X-Forwarded-For` header field whose value is
   exactly one address in canonical textual form: IPv4 dotted-quad, or IPv6 in RFC 5952 canonical
   form, with no port, no brackets, no zone identifier, and no list. That address is the accounting
   principal for every v1 and v3 connection, request, upgrade, and rate bound on that connection.
   A field that is absent, repeated, comma-bearing, or non-canonical is `400`
   `PROTOCOL.INVALID_FORWARDED_CLIENT` with the matching `forwarded_client_reason`. The server MUST
   NOT normalize, trim, or repair the value; it accepts the canonical form or rejects.
3. A direct connection uses the canonical socket address as its principal, keeps v1's rule that all
   of `127.0.0.0/8` and `::1` collapse to one loopback principal, and MUST ignore `Forwarded`,
   `X-Forwarded-For`, `X-Real-IP`, `Tailscale-User-Name`, and every other caller-supplied identity
   field.

The forwarded address is a rate-accounting key and nothing else. It authorizes nothing, selects no
entity, and appears in no message. Two connections that present the same forwarded address share
one budget; they do not share a controller, an entity, or a view.

### Display names

1. A proxy-forwarded connection MAY carry one `Tailscale-User-Name` field. The server trims ASCII
   spaces from both ends of its value and accepts the result if and only if it matches
   `common.schema.json#/$defs/display_name` exactly: 1 to 64 characters, all printable ASCII, from
   `[A-Za-z0-9 ._'@-]`, beginning and ending alphanumeric.
2. Any other outcome — the field absent, the field repeated, a byte outside `0x20..0x7E`, a
   non-matching value, a direct connection — yields the generated fallback `player-<n>`, where `n`
   is the server's monotonic connection ordinal for this session. The server logs the outcome at
   `warn` as structured data with a reason code and the received length, and never the received
   value.

   The ordinal is used rather than the entity id because a name is fixed exactly once, when the
   session opens and registers its directory entry, and the directory refuses a second registration
   so that no later frame can rename a player. At that instant no entity id exists: the controller
   id is that call's own result, and the body is created by a later tick applying the spawn the
   controller id is required to submit. An entity-derived name is therefore a cycle, not a naming
   choice. The ordinal is stable for the connection's life, unique among live sessions, and the same
   string appears in the welcome and in every peer's `controllable.display_name`.
3. **No character is ever substituted.** A published display name is either a byte-exact copy of a
   value the trusted proxy sent or the generated fallback. A sanitizer that replaces characters
   would turn one real name into a different real-looking name, which is a worse outcome than a
   visible `player-7`.
4. The server MUST NOT read `Tailscale-User-Login`, `Tailscale-User-ProfilePic`, or any other
   `Tailscale-User-*` field. `Tailscale-User-Login` is an email address, and every display name is
   published to every other connected peer.

The asymmetry between rules is deliberate: a malformed forwarded address is fatal because it is a
security control, and a malformed name is a fallback because it is a label. Neither is a credential.
Two players may hold the same display name and the client MUST NOT use it to identify anyone;
`controller_id` is the identifier.

### Entities, controllers, and what survives what

A connection owns exactly one live body at a time and exactly one controller for its whole life.

* `controller_id` is the durable identity of the deciding agent and is assigned once at admission.
  It is the only stable self-identifier a client has.
* `entity_id` is the identity of one body. It does not survive elimination, and it does not survive
  the match reset that destroys every player entity on the first `lobby` tick after `ended`
  (`0005-royale-mode.md` § "Elimination and placement"). The server seats the same `controller_id`
  on a new `entity_id`; the client observes the change in the next snapshot.
* `welcome.entity_id` is therefore the session's **first** body only. A client MUST resolve its own
  body each frame by finding the entity whose `controllable.controller_id` equals its own
  `controller_id`, and MUST treat "no such entity this frame" as the ordinary, expected state of a
  player who is eliminated, waiting for the next match, or deferred by the mode's spawn policy.
* A session whose body is absent still receives every snapshot and may still send commands. Those
  commands consume a rate token and are then discarded by `InputBatch::create`, which has nothing to
  write. They are not an error and MUST NOT close the connection, because elimination and an
  in-flight keystroke race by construction and closing on that race would disconnect honest clients
  at the most visible possible moment.
* A session takes a seat by asking, never by naming one. Whenever it observes a lobby in which it
  holds no seat it submits a server-issued `join`, which takes the lowest empty seat or, in `lobby`
  and `countdown`, the lowest-indexed NPC seat -- a person displaces a bot -- and it asks again
  every tenth of a second until it holds one. A bot created for a declared seat joins exactly that
  seat, and the server creates a bot for every declared seat that holds none.
* Closing the socket, however it closes, enqueues a server-issued `leave` for the session's
  `controller_id` before the controller is retired. The tick destroys every entity that controller
  drove -- seated, pending, or created from a spawn still queued at the moment of the close -- and
  vacates any seat it held, so nothing a session owned survives it.
* A reconnect is a new join: new request ID, new `controller_id`, new `entity_id`,
  `message_sequence` restarting at 1. Nothing is resumed and no state is recoverable. Resume tokens
  are future work (§ "Alternatives considered").
* Bots are indistinguishable from players to the simulation and distinguishable to a client by one
  field: `controllable.controller_kind` is `session` for a network player and the registered bot
  kind — `wanderer`, `chaser`, `scripted_replay` — otherwise. The simulation never branches on it
  (`0004-gameplay-architecture.md` § "Controllers").

## Server message model

The server sends only unfragmented UTF-8 text data frames, each containing one JSON document with no
leading or trailing non-whitespace bytes. Two schemas exist and no others: exactly one
`welcome-message` and then `snapshot-message` frames. There are no deltas, patches,
separate acknowledgement frames, lifecycle notifications, in-band error frames, or binary frames.
Snapshots carry a nullable, session-specific movement-tuning result beside the shared world.
Maximum encoded
frame payload is 2,097,152 bytes.

`message_sequence` counts every delivered application message on one connection. The welcome is
always `1`; the first snapshot is `2`. A client that receives a snapshot as its first frame has lost
the welcome and MUST close rather than proceed with an unknown `controller_id`.

`tick_sequence` is the committed simulation tick, strictly increases between snapshot frames on one
connection, and the server suppresses duplicate ticks. Clients MUST treat each snapshot as a
complete immutable replacement and MUST NOT merge it into prior state. Skipped ticks are visible in
`tick_sequence`; there is no replay.

Map bounds, positions, radii, hill geometry, and race course points are world-space values, not
viewport coordinates. A client may show a movable region of a larger map and choose its camera
independently of the controlled body. Camera centre, presentation scale, follow/manual selection,
and pixel dimensions are local presentation state; v3 defines no camera command or camera-filtered
snapshot. A client still validates the complete snapshot before selecting what falls in its view.
The current client already supports independent manual/follow cameras through one world
projection (ADR 0004 § "World space and the client viewport"); this requires no camera wire state.

### welcome

Sent once, immediately after the upgrade, before any snapshot. It carries `entity_id`,
`controller_id`, `display_name`, `mode`, `map`, `accepted_command_kinds`, `npc_controller_kinds`,
`lobby_id`, `seat_count_maximum`, `terrain`, and `movement_tuning_minimum_interval_milliseconds`.
The last member is `500`, the minimum interval between new tuning exchanges for one controller;
it does not replace the global command token bucket. The exact protocol version is
`meta.protocol_version`, which every frame carries; the welcome is simply the first frame that
carries it, and it is not restated in `data` because two sources for one value is the defect
`0005-royale-mode.md` § "Match section fields" refuses for the zone.

`accepted_command_kinds` is the intersection of the mode's `accepted_command_kinds()` with the
client-sendable vocabulary. It MUST NOT name `spawn`, `despawn`, or `leave`: those kinds exist in
the simulation's `Command` variant but are issued by the server -- a spawn on session admission, a
leave on session close, a despawn only by a fixture that names an entity -- never by a client, and
advertising them would name a capability the boundary must refuse. A mode with no
match to start — `sandbox` — publishes only `set_thrust`, so the four lobby controls are absent from
a client's welcome rather than drawn and inert. It also omits `set_movement_tuning`: cooperative
live tuning requires a seat, and Sandbox has no seated controllers or authority exception.

`npc_controller_kinds`, added in 2.3, contains only unprofiled NPC choices, in controller registry
order. Optional `npc_profiles` contains configured `{npc_kind, profile_name}` choices, in authored
profile order within registry order. The two projections come from one immutable `NpcCatalogue`
shared by session publication and runtime admission. A kind cannot occur in both partitions.
The plain partition has at most 64 entries; the profiled partition has at most 16 and is omitted
when empty. Names use the bounded lower-snake-case grammar. Numeric profile settings stay server-side.

A `seat_npc` declaration must match a complete choice: absent `profile_name` matches only a plain
kind; a present token matches only the exact advertised pair. Null is not omission. NPC seats
publish that same optional token before and after bot creation, and after the bot leaves. The
browser retains the welcome catalogue through snapshots and checks both outgoing declarations
and published NPC seats against it. A profile name is identity, not a client-authored configuration.
Adding a configured profile changes catalogue contents, not its schema. Sandbox advertises no
profiled choices because it supplies no stable authored-seat identity for tactical bots.

`lobby_id` and `seat_count_maximum`, added in 2.4, are the two facts about its room a session cannot
read from any snapshot. `lobby_id` is the room the session was admitted into, `1..8`: the number the
directory lists the room under and the one every log line about the session carries. It is
constant for the connection, and it is in the welcome rather than in `match` because a room does
not change under a session, and a snapshot that restated it on every frame would be a second source
for a constant. `seat_count_maximum` is the most seats the room's map can seat -- its spawn-marker
count, `1..64` -- and it is what bounds a client's `set_seat_count` control: 64 is the protocol's
bound, the map's is the room's, and a client that drew a control up to 64 on a four-marker map would
offer sixty settings the tick ignores. It is a map fact fixed for the process lifetime, so it is
published once here and never per snapshot.

**The advertisement is not the enforcement.** It exists so a client can render only controls it can
use. The boundary rejects an unaccepted kind independently, and `InputBatch::create` filters the set
a second time inside the runtime. A client that ignores the advertisement gains nothing — and a
client that names an NPC declaration outside the exact advertised catalogue is refused by the
same boundary that published it. The runtime independently checks this same catalogue before
mailbox insertion; an empty catalogue admits no NPC selection.

### Immutable terrain

`welcome.data.terrain` is required and carries the complete map geometry. Every object is
closed; no field is optional, no compiled arrangement, tolerance, color, revision, or future
mechanic is serialized. Units are world units and numbers follow the existing finite binary64,
round-trip-safe decimal and no-negative-zero policy.

| Field | Required value |
|---|---|
| `bounds` | `{width_world_units, height_world_units}`, both finite, positive, at most `1e9` |
| `ground` | `solid` (the full envelope) or `corridors` (the positive corridor union) |
| `corridors[]` | `{name, half_width, points: [{x, y}, ...]}` |
| `holes[]` | `{name, center: {x, y}, radius}` |

There are at most 8 corridors, 32 total segments, 40 total points, and 32 holes.
Each corridor has at least two points; consecutive points have finite positive squared
distance. Half-widths and radii are finite, positive, and at most `1e9`. Names use the
bounded 64-character snake-case wire-name grammar and are unique within each family.
Authored points and hole centers lie in the closed envelope. Widened road edges and whole
hole discs need not fit inside it. Solid ground forbids corridors; corridor ground requires
at least one. Authored array order is preserved.

The browser validates schema and every semantic constraint before publishing welcome to
its consumer. Terrain bounds must exactly agree with the already validated v1 configuration.
Invalid or absent terrain fails visibly, never becoming a fallback rectangle or clipped partial
success. The renderer uses the existing camera projection: envelope intersect positive ground
union, minus the union of all holes. Overlapping holes remain void, and painting a later road
must not refill them. Race draws gates and objectives over that shared layer, not another road.
The simulation's tolerance/rim convention remains owned by its canonical terrain queries;
raster antialiasing does not define gameplay support.

In-process `WorldSnapshot` retains an aliasing shared immutable handle to the actual terrain
inside the simulation-owned map; observations expose that same object. Retained snapshots
survive simulation destruction and equality compares authored values, not pointer identity.
Welcome is constructed from that explicit terrain value. No snapshot frame serializes terrain.

The Step 7 development checkpoint temporarily carried equality-tested race `track` and
`track_half_width` mirrors. Step 8 removes both fields and publishes the required `road` identity
alongside objectives. The selected corridor's geometry exists only in welcome terrain; no reader
assumes it is named `road` or selects the first corridor. There is no mirror compatibility path.

### snapshot

`data` is `tick_sequence`, `random_draw_counts`, `entities`, `match`, and `tuning_result`.

`random_draw_counts` is the required closed object `{hazards, hill}`, in the simulation stream
registry's stable order. Each count is an integer in `[0, 2^53-1]` and records draws consumed by
that stream in the committed world. Stream initialization consumes no draws. Snapshots expose
counts only, never match seeds or generator state. Counts remain full `uint64` values in C++;
the encoder rejects a count above the wire ceiling with
`PROTOCOL.ENCODING.RANDOM_DRAW_COUNT_OUT_OF_RANGE` and context
`snapshot_message.data.random_draw_counts.<stream>`, rather than rounding, clamping, or omitting it.
This member is added in Step 9; the replaced C++ `random_draw_count` scalar was never a v3 JSON
member. Closed schema validation rejects absent counts, missing streams, and unknown stream keys.

`entities` is ordered by ascending `entity_id`, contains no duplicate id, and represents one
coherent tick. **Every published entity counts**, including map static bodies and the zone entity,
not only players. Each entry is `entity_id` plus a closed `components` object keyed by component
kind, with at least one component; an entity with no components is unrenderable and MUST NOT be
published. Within `components`, keys are encoded in ascending component-kind name order.

`match` is `mode`, `phase` (`lobby`, `countdown`, `running`, `ended`), `phase_started_tick`,
`seats`, `start_requested`, `movement`, `outcome`, `placements`, and `mode_state`.

`movement` is shared committed state: `{current, defaults, limits, revision, effective_tick}`.
Both pairs contain `acceleration_world_units_per_second_squared` and
`normal_top_speed_world_units_per_second`. Their limits are finite `[0, 10000]` and `[1, 10000]`
respectively; `limits` uses those same keys, each with `{minimum, maximum}`. These are tuning
parameter limits, not a certified physical or capacity envelope. `defaults` is the room's authored
pair, never a hardcoded client preset, and live changes do not alter it. `revision` is a safe
nonnegative integer; `effective_tick` is zero exactly when revision is zero, otherwise positive
and no later than this snapshot. Each successful change increments revision once, including an
equal-pair Apply. The pair and revision survive body replacement and match lifecycle transitions.

`tuning_result` is required and nullable, outside `match` because it belongs only to the receiving
session. A non-null value is `{tuning_request_id, status, decision_tick, revision,
retry_after_milliseconds}`. Committed statuses are `applied`, `superseded`, `stale_revision`,
`not_seated`, and `revision_exhausted`: they carry the positive committing tick and resulting safe
revision, with a null retry interval. `applied` and `superseded` require a positive revision;
`revision_exhausted` requires `2^53-1`. Admission refusals `rate_limited`, `mailbox_full`, and
`mailbox_evicted` carry null tick and revision. Only `rate_limited` carries a non-null retry interval,
an integer in `[1, 500]` milliseconds, rounded up from the remaining steady-clock deadline.

The encoding boundary and single-frame conformance oracle require any result's decision tick to
be covered by the snapshot tick and its revision not to exceed `match.movement.revision`.
The client additionally requires exactly its pending request id; unsolicited, future, duplicate,
or malformed results fail before sequence acceptance or snapshot publication. An applied result
must be `pending.expected_revision + 1` without overflowing the safe-integer ceiling. If that
revision is also the current snapshot revision, its pair must equal the requested pair and its
effective tick must equal the decision tick. A later snapshot may truthfully cover an older result;
the client never infers request success from a changed room revision alone.

`seats` and `start_requested`, added in 2.3, are the **pre-match lobby**: the ordered seat roster the
first transition reads, and whether somebody has pressed Start for it. They sit with the lifecycle
header they gate rather than beside `outcome` and `placements`, which describe a match already
played. A seat is `{kind, controller_id, npc_kind}` with `kind` one of `empty`, `controller`, `npc`;
every member is always present and the member that does not apply is `null`, which is the shape
`outcome` already uses so that a decoder reads one known member set rather than branching on which
keys exist. An `npc` seat with a `null` `controller_id` is a seat whose bot the server has not
created yet — the joining state, not a missing value, and not a filled seat: a match starts only
once every seat holds a controller, so a lobby of declarations cannot start a match with nobody in
it.

`seats` is an array so its length **is** the seat count; there is no separate count member, because
two sources for one number is the defect this section refuses everywhere else. A world that declared
no lobby publishes an empty array rather than a `null`, so a decoder has one code path, and an empty
roster is never full, so no client can read it as a startable match.

`start_requested` is one-shot: the server clears it on every arrival in `lobby`, so a finished match
cannot restart itself and a client can explain, from these two members alone, why Start is or is not
about to fire.

`phase_started_tick` admits `0`, and its schema type is
`phase_start_tick` rather than `tick_sequence` for that reason. A match begins in `lobby` at load,
before tick `1` exists, and no transition has been committed for the whole of that first lobby, so
`0` is the truthful report of "this phase has always been the phase". A client renders an elapsed
phase time from it only once it is nonzero.

`outcome` is `{kind, winner_entity_id, winner_team_id}` with `kind` in
`none | won_by_entity | won_by_team | drawn`. Both winner members are always present and the
inapplicable one is `null`; the schema enforces the pairing. Two named members rather than one
polymorphic `winner` is deliberate: an entity id and a team id are different id spaces, and one
field holding either is a type confusion a renderer resolves by reading a sibling discriminator —
which is exactly the read that gets forgotten and highlights the wrong blob.

`placements` is the ordered finished ranking, bounded at 1,024. Each entry is
`{entity_id, controller_id, placement, eliminated_tick}`. `controller_id` is carried so a client can
recognize its own result after its `entity_id` has been destroyed. Placement semantics — shared
placement for a simultaneous elimination, no entry for the winner, placement `1` for a mutual
finish — are `0005-royale-mode.md` § "Elimination and placement" and are not restated here.

`mode_state` is `{schema_id, value}`. A mode with no non-entity-shaped state publishes
`blob-royale://protocol/v3/mode-state/none` and an empty `value`, so a decoder has one code path
rather than a nullable branch. `royale` publishes
`blob-royale://protocol/v3/mode-state/royale` carrying `previous_phase` and
`elimination_grace_ticks`. `king_of_the_hill` publishes
`blob-royale://protocol/v3/mode-state/king-of-the-hill` carrying three declared constants,
`points_to_win`, `point_interval_ticks`, and `time_limit_ticks`; its scores are `score` components,
its hill is the `hill` component of the hill entity, and its `placements` array is empty.
`hill_presence` is partial progress toward the next point. The hill removes it for a knockout on
the knockout tick after scoring, so a completed point remains earned and even a zero-delay return
cannot carry partial presence across the lost body.

`race` publishes `blob-royale://protocol/v3/mode-state/race`: `road`,
`checkpoint_radius`, the ordered point array `checkpoints`, `time_limit_ticks`,
`finish_window_ticks`, and the recorded `standings`. Each standing is
`{entity_id, controller_id, placement, finished_tick, finished_tick_offset}`; equal certified times share a placement
and appear in ascending entity order. The final checkpoint is the finish. `road` is a nonempty
snake_case identity of at most 64 characters naming exactly one corridor in the session's retained
welcome terrain. The snapshot encoder validates this binding against its snapshot terrain; the
browser validates it against retained welcome terrain before accepting sequence state or publishing
the snapshot. `checkpoint_radius` MUST NOT exceed that corridor's `half_width`. A structurally
valid name missing from terrain is a validation error, never a first-corridor fallback. The
standalone single-frame oracle has no previous welcome context and cannot certify this binding.
Production tick-zero snapshots may still carry `NoModeState` (wire schema id `none` with an empty
value object); no initialization tick or empty road sentinel is introduced. The generic `placements`
array is empty because its `eliminated_tick` describes an elimination, and finishing leaves a
racer's body in play. An empty `standings` array means nobody has finished. The recorded
`controller_id` identifies a session's finish even after the entity disappears. `race_progress`
counts gates taken; it does not imply a distance ranking among unfinished racers.

`finished_tick_offset` is the certified normalized fraction in `[0,1]` within `finished_tick`.
Compare tick first, then offset, then entity identity; never add offset to a large binary64 tick.
Zero and fractional offsets are valid. A finish ends remaining movement in that tick and releases
input, while preserving the body. The HUD exposes the tick and fraction separately.

Before the first finish, the running time limit is measured from `phase_started_tick`. Once a
standing exists, `finish_window_ticks` is measured from the first standing's `finished_tick` and
replaces that limit. A return countdown comes from `respawn_timer.ticks_remaining`; when the timer
has been erased but a racer still has progress and no body, it is waiting for a seating attempt or
a clear return point. These readings use committed ticks, never the message's wall-clock timestamp.

The mode configuration factories enforce publication bounds before any frame is built. Hill
radius remains at most `10^12`, and hill `points_to_win` is at most `2^53 - 1`; equality is legal
and their lower bounds remain a positive dimension and at least one point. Race's selected
terrain half-width is at most `10^9`, and checkpoint radius cannot exceed that half-width. The
standalone race radius schema retains its structural `10^12` ceiling, but the contextual binding
check imposes the tighter effective bound. No unrelated physical/hill scalar bound is narrowed.

**Entity-shaped state appears only as components.** The zone's center and radius are the `zone`
component of the zone entity and are not `match` fields. Alive count is not a field either: it is
the number of published entities carrying both `physics_body` and `controllable`, counted by the
client from the array it is already rendering. Publishing either twice would give a client two
sources for one value and a way to disagree with itself.

`controllable.commands_this_tick` exists in the simulation and is **not** published. A snapshot that
carried every player's live input would hand every peer a same-frame reaction advantage over every
other peer, and no rate limit or client-side rule can undo a disclosure.

`controllable.input_generation` is deliberately public: an optional positive committed tick
identifying the latest input invalidation. It is not intent or a hidden target. Omission means
the entity has never been invalidated; once present it survives stun expiry and same-entity body
return. It MUST NOT exceed the snapshot tick. The `stun` component publishes the same absolute
`activation_tick` and `expiry_tick` to network and in-process observers, with positive activation,
strictly later expiry, and activation no later than the snapshot tick. The lock is active exactly
when `activation_tick <= tick < expiry_tick`; no client wall clock unlocks it. The status system
normally erases expired components, but readers evaluate the interval rather than treating mere
component presence as an unconditional lock.

### Object member order

`contact_effect_admission` is a public, body-bound sparse component. Its sole required member is
`policy: "any_touch"`; an entity carrying it MUST also carry `physics_body`. Absence means
`closing_impact`, and a redundantly stored/transmitted closing-impact component is invalid.
Any-touch admits certified grazing and stationary/overlapping contacts for the source object's
effects; it does not grant an impulse without closing impact, change collision masks, or turn
center-based cliff support loss into a body-rim contact. Its state is cleared with its body.

JSON object order is not semantically significant to a general decoder, but `blob_protocol` MUST
encode in this order so golden bytes, logs, and repeated tests are deterministic:

* Envelope: `data`, `error`, `meta`.
* Welcome data: `entity_id`, `controller_id`, `display_name`, `mode`, `map`,
  `accepted_command_kinds`, `npc_controller_kinds`, optional `npc_profiles`, `lobby_id`,
  `seat_count_maximum`, `terrain`, `movement_tuning_minimum_interval_milliseconds`. Profile entries
  encode `npc_kind`, `profile_name`. The command-kind and plain-kind arrays
  are encoded in their schema enum's own order, except `npc_controller_kinds`, which is encoded in
  the server's registry order because that order is a deliberate ordering of the bots rather than a
  vocabulary.
* Terrain: `bounds`, `ground`, `corridors`, `holes`. Bounds: `width_world_units`,
  `height_world_units`. Corridor: `name`, `half_width`, `points`. Hole: `name`, `center`, `radius`.
  Points/centers: `x`, `y`. Corridor and hole arrays retain authored order.
* Lobby directory data: `lobbies`, in `lobby_id` order. Listing: `lobby_id`, `mode`, `map`,
  `phase`, `phase_started_tick`, `tick_sequence`, `seat_count`, `seat_count_maximum`,
  `filled_seat_count`, `npc_seat_count`, `session_count`, `healthy`. Its metadata is
  `protocol_version`, `schema_id`, `request_id`: the HTTP envelope's three.
* Snapshot data: `tick_sequence`, `random_draw_counts`, `entities`, `match`, `tuning_result`.
* Random draw counts: `hazards`, `hill` (the closed stream registry order).
* Entity: `entity_id`, `components`; component keys ascending by kind name.
* `contact_effect_admission`: `policy`.
* `race_progress`: `next_checkpoint`.
* `physics_body`: `position`, `velocity`, `acceleration`, `radius`, `mass`, `collision_layer`,
  `collision_mask`, `is_static`, `ground_attachment`.
* `controllable`: `controller_id`, `controller_kind`, `display_name`, then optional `input_generation`.
* `stun`: `activation_tick`, `expiry_tick`.
* `zone`: `center`, `radius`. `hill`: `center`, `radius`. `vector2`: `x`, `y`.
* `hill_motion`: `velocity`; its vector uses `x`, then `y`. No retarget schedule or stream identity is published.
* Match: `mode`, `phase`, `phase_started_tick`, `seats`, `start_requested`, `movement`, `outcome`, `placements`,
  `mode_state`.
* Movement: `current`, `defaults`, `limits`, `revision`, `effective_tick`. Each pair and the limits
  object: `acceleration_world_units_per_second_squared`, `normal_top_speed_world_units_per_second`.
  Each limit: `minimum`, `maximum`.
* Non-null tuning result: `tuning_request_id`, `status`, `decision_tick`, `revision`,
  `retry_after_milliseconds`.
* Seat: `kind`, `controller_id`, `npc_kind`. Seats are encoded in seat-index order.
* Outcome: `kind`, `winner_entity_id`, `winner_team_id`.
* Placement: `entity_id`, `controller_id`, `placement`, `eliminated_tick`.
* Mode state: `schema_id`, `value`. Within `royale`'s value: `previous_phase`,
  `elimination_grace_ticks`. Within `king_of_the_hill`'s value: `points_to_win`,
  `point_interval_ticks`, `time_limit_ticks`. Within `race`'s value: `road`,
  `checkpoint_radius`, `checkpoints`, `time_limit_ticks`, `finish_window_ticks`, `standings`.
  Each course point is `x`, `y`; each standing is `entity_id`, `controller_id`, `placement`, `finished_tick`, `finished_tick_offset`.
* Message metadata: `protocol_version`, `schema_id`, `request_id`, `message_sequence`,
  `sent_at_utc`.

IDs, sequences, and counters never exceed `9,007,199,254,740,991`. Every physical component is a
finite binary64 value encoded with a round-trip-safe decimal representation; `-0` is forbidden.
Units follow
[`0003-deterministic-simulation-contract.md`](../architecture/0003-deterministic-simulation-contract.md):
position `wu`, velocity `wu/s`, acceleration `wu/s²`, radius `wu`, one tick exactly `1/400 s`. The
network performs no interpolation, prediction, collision calculation, or unit conversion.

### Cadence delta

v1 § "Presentation cadence and stale replacement" applies in full, with one addition ahead of it.
Immediately after the upgrade the session requests one egress admission for the welcome frame. Until
that write completes the session holds no pending snapshot and retains no snapshot reference; if
admission is denied it retries at the next presentation slot. **The first snapshot MUST NOT be
written before the welcome**, because a client that sees world state before it knows its own
`controller_id` cannot tell which blob is its own and would render a guess.

Snapshot scheduling after the welcome remains v1's algorithm: one active write, one replaceable pending
immutable reference, replacement only by a newer tick, admission against the same global egress
budget, deadlines advancing from the prior scheduled deadline, and no catch-up burst. Slow clients
lose intermediate presentation snapshots by design and never slow or mutate the simulation.

After egress admission and active-write reservation, the session claims at most one covered tuning
result before encoding. Claim atomically frees that controller's runtime exchange slot. The active
write owns the claimed value until completion or teardown; its callback clears only that local
value, never the runtime slot for a later request. An encoding or transport failure after claim
does not replay the result: a disconnected client with an unresolved request reports `unknown`.

## Client command model

Application data is now bidirectional, which is the single largest change in the threat surface
between v1 and v3: **v1 never parsed a byte the client chose, and v3 does.**

A client data message is one JSON document validating against `command-envelope.schema.json`:
`{kind, payload}` and nothing else. The envelope carries no entity id, no protocol version, no
request id, and no client ordering sequence number. The tuning payload alone carries a bounded
correlation id, not an ordering stamp.

* **No entity id, and no controller id.** The server stamps the sending session's current body on a
  command that names an entity, and the durable identity it issued on a command that names a sender.
  There is no field for a client to put someone else's id in, so "ignore the client's entity id" is
  not a check that a refactor can drop. The four lobby commands carry the sender's stamp for exactly
  this reason: a `start_match` a client could sign with somebody else's identity would let one peer
  spend another's decision.
* **No protocol version.** Version is a property of the connection, fixed at the subprotocol token.
  A per-message version would be a downgrade lever pointed at the server's own decoder.
* **No client sequence number.** Within one tick the last command of a kind for an entity wins
  (`0004-gameplay-architecture.md` § "Commands"). A client cannot make an older command win by
  numbering it, and the rate bucket bounds how many can arrive in a tick.
  `tuning_request_id` correlates one tuning exchange and enforces admission uniqueness; it never
  selects a contender, changes canonical command ordering, or resumes a session.

### Admission order

Each inbound application data message is processed in exactly this order, and each step's failure is
terminal for the connection with the named close code. The order is the contract: charging the rate
token before JSON parsing is what keeps a peer from buying unbounded parser work with one token.

1. **Frame size.** Over 1,024 bytes → close `1009 client_message_too_large`. This is v1's inbound
   limit, unchanged, and it applies before any buffering completes.
2. **Transport validity.** Invalid UTF-8 → close `1007 invalid_utf8`; invalid framing or control
   semantics → close `1002 protocol_error`. Both are v1 rules at the transport layer.
3. **Rate token.** Consume one token from the per-session command bucket. An empty bucket closes
   `1008 command_rate_exceeded`. **No JSON parsing has occurred yet.**
4. **JSON parse.** Not a single well-formed JSON object, or containing a non-standard literal such
   as `NaN` or `Infinity` → close `1008 command_malformed`.
5. **Envelope shape.** Fails `command-envelope.schema.json` at the envelope level — missing member,
   extra member, non-object payload → close `1008 command_malformed`.
6. **Kind acceptance.** `kind` is not a registered v3 client command kind, or is registered but
   absent from this match mode's accepted set → close `1008 command_kind_rejected`.
7. **Payload validity.** `payload` fails the closed schema for its kind — extra member, wrong type,
   out of range, non-finite → close `1008 command_payload_invalid`.
8. **Stamp and submit.** Build the `Command`, stamp the session's current `EntityId` or its
   `ControllerId` according to which identity the kind addresses, and submit to the write-only
   `CommandSink`. If a kind that names an entity arrives while the session owns no body, the command
   is dropped and the connection stays open. **A kind that names only its sender is submitted
   whether or not the session owns a body**, which matters: a session owns none for the whole window
   between a lobby wipe and its reseat, and none at all while a full spawn ring defers it, and both
   are exactly the moments a player is looking at the lobby deciding a seat count and pressing
   Start.

Failing closed on a malformed command rather than ignoring it is the deliberate choice. A client
that sends a shape the server does not recognize has a bug or is probing; continuing the session
would make both invisible.

Standard close, ping, and pong control frames remain allowed under v1's separate control-frame
budget (five in a burst, one per second, excess closes `1008 control_rate_exceeded`). The control
budget and the command budget are separate ledgers; a peer cannot spend one on the other.

### set_thrust

`{x, y, input_generation?}`, closed; x/y are finite numbers in `[-1, 1]` and a present generation
is an integer in `[1, 2^53-1]`. Optional means omitted, never null or zero. The per-component bound admits `(1, 1)`, whose
magnitude is `sqrt(2)`. **Magnitude clamping to 1 is a mode rule** applied by `thrust_steering`
(`0005-royale-mode.md` § "Steering"), not a wire rule, so a client cannot obtain 41 percent more
acceleration by thrusting diagonally. Stating the bound only per component and leaving the magnitude
to the mode is the arrangement that makes the diagonal-speed exploit a mode invariant with a fixture
rather than a schema detail nobody re-derives.

A thrust records magnitude-clamped input intent, preserving subunit analog magnitude. Steering
reads the current shared movement pair each tick, scales that intent by the shared acceleration,
and limits only that propulsion contribution at normal top
speed; it does not clamp externally acquired overspeed. A client that stops sending does not stop thrusting;
releasing a key MUST send `{x: 0, y: 0}` with the same optional generation captured for that
activation. A fresh press captures the latest observed generation. Its aim updates and release
keep that token; no queue, flush, connection, or decoder may retag old input with a newer value.

The authoritative steering system ignores commands while stunned and requires exact optional
generation equality after expiry too, including zero releases. Absence is not a wildcard. Stun
clears stored intent to explicit zero and clears propulsion acceleration; stale commands do not
replace valid intent or queue automatic resumption. Each positive applicable stun request sets
generation to its committing tick, including one that does not extend an existing longer stun.
Multiple requests within that tick share the token. Last-submission-wins input coalescing is
unchanged, so a stale submission may supersede a valid pending submission and then be ignored.

The browser cancels held/pending Space activation on generation change even if all active-stun
snapshots were skipped, and requires a fresh press to resume. Same-entity respawn retains this
generation. The guarantee ends at entity destruction: ingress still stamps the current entity,
and detecting a completely invisible destruction/reseat is outside this contract. No production
stun command is introduced; Step 14 is the status foundation, with the impact producer in Step 18.

### set_movement_tuning

The closed payload is `{tuning_request_id, expected_revision,
acceleration_world_units_per_second_squared, normal_top_speed_world_units_per_second}`. The request
id is an integer in `[1, 2^53-1]`, expected revision in `[0, 2^53-1]`, and the pair uses the published
intrinsic limits. The session stamps its controller, never a client-supplied identity. Availability
comes from the mode's accepted mask. In modes that support it, any seated controller may apply a
change in any phase; absence of a body is not absence of a seat.

After unchanged preparse rate limiting and payload validation, ids must strictly increase within
one controller lifetime (gaps are allowed). Reuse or a nonincreasing id closes `1008
tuning_request_id_reused`, checked first. A well-formed new id advances the high-water mark;
another unresolved exchange then closes `1008 tuning_request_in_flight`, leaving the prior request
unknown to the disconnected client. No slot is overwritten and no unbounded refusal queue exists.
An eligible new exchange starts a 500 ms admission deadline even if the mailbox is full; a rate
refusal does not extend that deadline. A claimed terminal result frees the slot before its frame
is written, so a legitimate next Apply after receiving it is not mistaken for pipelining.

The tick resolves accepted contenders using canonical command order and the revision at tick
entry, after thrust and before Start. The last eligible seated contender wins; peers based on a
different entry revision are `stale_revision`, an earlier eligible contender is `superseded`, and
an unseated sender is `not_seated`. At the maximum revision no increment is attempted and the
result is `revision_exhausted`. Decisions become deliverable only after the tick commits; rollback
never manufactures a committed outcome.

The browser uses the existing `sendCommand` path and an explicit `idle | pending | resolved |
unknown` exchange state. It reserves pending before socket send, handles synchronous result
delivery, and reports unknown if delivery becomes uncertain. Local validation or pre-send refusal
is not a server rejection. Disconnect/reconnect never automatically replays a tuning command;
a new controller gets a new id sequence. Room changes clear the previous room's exchange state,
while an interrupted same-room retry preserves its honest unknown outcome. Controls are deferred
to Step 11; Step 10 supplies the API and result state only.

### The lobby commands

`set_seat_count`, `clear_seat`, `seat_npc`, and `start_match`, added in 2.3, are a client's
authority over lobby setup: which seats exist, who is cleared out of one, which NPC fills one, and
whether to begin. Each payload is closed and names no sender.

**Anyone in the lobby may send any of them.** There is no host, no ready check, and no per-seat
ownership. That is a deliberate trust choice for a private tailnet where every peer is an identified
person the deployment invited, and where the worst outcome of a mis-click is a match that starts
early or a bot that has to be re-seated. **A public deployment would have to change the identity that
reaches the tick, not these payloads**: a lobby command would need an authority attached to its
`ControllerId` — host, or seat-owner, or first-joiner — decided above the simulation and refused at
the sink, because the tick knows nothing about people and must not start.

**Two kinds of failure, and the line between them is whether the client could have known.**

* A **value** the published contract does not describe — a seat index or seat count outside its
  schema bound, a fractional one, a declaration outside the advertised NPC catalogue, an extra member — is
  `command_payload_invalid` and closes the connection, exactly as an unregistered `command_kind` or
  an unregistered `mode_state.schema_id` does. Every one of those is constant for the process
  lifetime and was handed to this client in its first frame.
* A **disagreement with committed state** — the match is not in `lobby`, the seat index names no
  seat in the current roster, the seat a `seat_npc` names is already occupied, a `set_seat_count`
  would shrink past an occupied seat or grow past the running map's spawn markers — is silently
  ignored by the tick and the connection stays open. The roster changes under a client between
  frames and racing it is unavoidable, so a disconnect there would punish an honest client for the
  server's own timing; and the marker count is a fact about the map that no frame publishes, so a
  client could not have known it.

The stated rules, each of which a client can render before the fact:

* Seating fills an **empty** seat and never replaces an occupied one, so two clients seating one seat
  in one tick resolve by the batch's existing order — ascending sender within the kind — and the
  second press is a no-op rather than an eviction. Replacing an occupant is `clear_seat` then
  `seat_npc`, which the server applies in that order within a single tick.
* Clearing empties a seat whose kind is `npc` and leaves a seat whose kind is `controller` alone. A
  controller seat belongs to a live session, and only the runtime may give or take it.
* **A lobby never shrinks past somebody who is sitting down.** A `set_seat_count` that would remove an
  occupied seat — held by a person, or declared for a bot whether or not the bot exists yet — changes
  nothing; growing appends empty seats at the high indices, so no existing seat changes index. A
  client renders the rule by flooring its seat-count control one above the highest occupied seat. Truncating and compacting were both rejected: truncation makes one player's slider the
  most destructive control in the room, and compaction renames every seat below the gap and moves
  people without telling them.
* `start_match` records a request and commits nothing. The server commits `lobby -> countdown` only
  when the running mode's objective also says the field is complete — for royale, every seat holds a
  controller, a person's or a created bot's, so an `npc` seat still joining does not count — so a
  press into a lobby with an empty seat is remembered rather than lost, and a press while a match runs is refused by the phase
  guard rather than arming the next match from inside this one.

## Versioning and fail-closed decoding

Adding a component kind, a client command kind, a mode-state schema, a member to any already
published block, or an HTTP target in a released contract is a **minor** version (for example `3.1`). It
republishes this schema set with the addition registered and the `protocol_version` const bumped.
Removing a kind or a member, renaming one, or changing what one means is a **major** version and
needs a new route and subprotocol, exactly as v1 to v3.

**Changing the contents of the welcome's NPC catalogue is not a version change.** Plain kinds and
kind/profile pairs are startup data rather than schema enums. Registering a bot or configuring a
profile changes what these projections carry, not their shape. Their bounds are protocol constants,
not the registry's current size. Adding the profile fields themselves belongs to the coordinated,
still-in-development 3.0 release; this does not authorize adding unknown fields to a released version.

A new member is a minor for the same reason a new kind is: the schemas are closed, so a 3.0 client
validating a future 3.1 frame fails on the member it does not know, and the version-first rule below is
what turns that into an explicit close rather than a validation error a client might paper over. An
optional member still requires that version change. Omission must have an explicit meaning in
the schema and this contract: absent `npc_profiles` means no profiled choices, and absent
`profile_name` means an unprofiled declaration. It never requests a default profile.

| `3.0`, Step 8 | Remove race `track`/`track_half_width`; publish required selected `road` identity; validate its terrain binding and gate-radius bound; racer reads the same corridor through the proven canonical projection query. Gates, clocks, standings, and gameplay remain unchanged. |

The version constant moves once for this plan. Later features add their schema, encoder/decoder,
generated types, client validation, examples, and row here in the same commit as authoritative
behavior. No command or vocabulary is reserved or advertised early. These development commits
are not separately deployable releases; server and assets ship together only after final
verification. Released-protocol versioning rules resume after that coordinated release.

**A client MUST fail closed on a kind it does not know.** It MUST NOT ignore an unknown component
kind, an unknown command kind, or an unregistered mode-state schema id and continue rendering. The
mechanism has two parts:

1. **Version first.** A client reads `meta.protocol_version` before validating or interpreting the
   rest of a frame. A different major, or a minor greater than the client's own compiled minor, is
   close `1003 client_version_unsupported`. This is the only ordering in which a client can respond
   to a document it cannot validate.
2. **Closed schemas after.** `entity-snapshot.schema.json` closes `components`,
   `command-envelope.schema.json` closes `kind`, and `mode_state_schema_id` is a closed enum rather
   than a grammar. A kind the schema set does not name is a validation failure, and a validation
   failure on a server frame is close `1003 client_kind_unsupported`.

**This matches `0004-gameplay-architecture.md` § "Versioning discipline".** Ignoring an unknown
component or mode-state schema can silently omit an obstacle or objective from the client's
understanding of the world. Fail-closed decoding prevents that disagreement about what a frame
said. A client logs the unknown kind by name once before closing. This rule does not demand that
every entity be visible simultaneously: intentionally clipping known geometry outside a viewport
is valid presentation, provided the whole frame was validated and the authoritative snapshot is
not discarded or rewritten to match the camera. Offscreen is not unknown.

`welcome.accepted_command_kinds` lets a client discover a *narrowing* without a version change: a
mode that accepts fewer kinds than the version registers is normal and is not a failure, and since
2.3 it is how `sandbox` says it has no lobby. The two NPC catalogue projections allow changes in
selectable labels without a version change, for the reason given above.

## Limits

v1 § "Resource and rate policy" applies in full, with the accounting principal replaced per
§ "Identity" and these bounds added or changed.

| Resource | Bound | Action at bound |
|---|---:|---|
| Client commands per session | Token bucket: capacity 30, refill 20/second | Close `1008 command_rate_exceeded` |
| New movement-tuning exchange | One unresolved exchange per controller; minimum 500 ms between eligible new exchanges | Correlated `rate_limited` with retry interval; overlapping unresolved id closes `1008 tuning_request_in_flight` |
| Inbound application message | 1,024 bytes | Close `1009 client_message_too_large` (v1 bound, now reached by real traffic) |
| Entities in a snapshot | 1,024 total, all kinds | Reject configuration/startup; never truncate the array |
| Placements in a match section | 1,024 | Reject; never truncate |
| Each published random draw count | Integer `0..2^53-1` | Encoder invariant failure with the stream name; never round or clamp |
| Seats in a match section | 64 | Encoder invariant failure; never truncate. A running map's spawn-marker count is the tighter bound: enforced at startup for the configured count, and a `set_seat_count` above it is ignored by the tick. |
| Plain NPC kinds in a welcome | 64 | Reject at startup; never truncate |
| Profiled NPC choices in a welcome | 16 | Reject at startup; exact pairs, no overlap with plain kinds; never truncate |
| Terrain in welcome | 8 corridors; 32 total segments; 40 total points; 32 holes; 64-character names | Reject invalid authored or received data; never truncate |
| Outgoing welcome payload | 2,097,152 bytes | Bounded serialization failure; never truncate geometry or bypass egress admission |
| Outgoing snapshot payload | 2,097,152 bytes | Internal invariant failure; never truncate |

| Outgoing directory document | 65,536 bytes | Internal invariant failure; never truncate. Eight listings at every bound fit in a twentieth of it. |

The command bucket uses `steady_clock`, never goes negative, and is per session rather than per
principal, so one tab cannot starve another tab of the same player. It is created at admission and
destroyed with the session.

**The v1 pair of 4,096 items and a 2 MiB frame does not survive the component model, which is why
the entity bound is 1,024.** A v3 entity is much larger than a v1 player row. Measured against these
historical component schemas at their bounds — every scalar at its extreme, every string at 64 characters, every id at
`2^53-1`:

These inherited historical row measurements explain the entity ceiling; they are not a new
v3 maximum-frame measurement. Current complete-message tests prove encoding under its bound,
including a maximally populated legitimate terrain welcome and exact-byte/one-byte-short budgets.

The Step 7 maximum-cardinality complete welcome measures **10,332 bytes** in the advisory
Mac-hosted Linux/amd64 GCC check: 8 corridors, 40 points, 32 holes, and 64 NPC kinds with bounded
names/IDs/request ID. Its exact-byte budget succeeds and a one-byte-short budget fails visibly.
This is a tested complete-message specimen, not a mathematical maximum over every legal numeric
spelling and not a native capacity/performance certification.

| Historical row | Recorded compact bytes |
|---|---:|
| One entity carrying all eight component kinds | 934 |
| One entity carrying `controllable`, `physics_body`, `zone_exposure` (a player) | 681 |
| One placement entry | 116 |
| One seat entry | 105 |
| 64 seats (the whole lobby, every seat at its bounds) | 6,720 (0.3% of the frame ceiling) |
| 1,024 entities + 1,024 placements | 1,075,200 (51% of the frame ceiling) |
| 2,048 entities + 2,048 placements | 2,150,400 (102.5% — over) |
| 4,096 entities + 4,096 placements | 4,300,800 (205% — over) |

Keeping v1's 4,096 would make a schema-legal snapshot unencodable, and v1's rule for an oversized
frame is a hard invariant failure that stops the process. That is a remotely reachable availability
kill triggered by joining, and 1,024 with a 2× margin removes it. 1,024 is also far above the
deployed ceiling of 32 concurrent sessions plus a configured bot roster plus a map's static bodies.

`kMaximumPlayerCount` in `src/simulation/simulation_limits.hpp` is `4,096` and is now looser than
the protocol. **Startup MUST reject a configuration whose map static bodies, plus the zone entity,
plus the roster ceiling, can exceed 1,024 published entities**, in the same way v1 validates
`width_world_units > 2 × player_radius_world_units` before accepting traffic. The encoder MUST still
fail closed if the bound is ever exceeded at run time; it never truncates and never drops an entity.

## Trust boundaries and threat cartography

The lenses are trust-boundary analysis, STRIDE over the new bidirectional decomposition, and abuse-
case enumeration against the specific thing v3 adds: a client that can cause an effect.

### Assets and principals

v1's five asset rows are unchanged. v3 adds seven.

| Asset | Protected property | Principal that owns it |
|---|---|---|
| A player's control of their own body | Exclusivity: only this session's commands move this entity | `SessionWebSocketSession` entity stamp + `CommandSink` |
| Tailnet-derived display name | Bounded, non-injecting, disclosed only as a label | HTTP boundary sanitization |
| Command admission budget | Bounded inbound parse and CPU per session | Per-session command token bucket |
| Match integrity | Placement and outcome derived only from committed ticks | `MatchLifecycleSystem`; no network input reaches it |

| A seat in a specific room | Contended and finite: at most the room's `seat_count` admitted sessions, gated before a controller is issued; a person displaces only a bot, never another person | Room admission (`409 LOBBY.FULL`) and the tick's `apply_join` (`src/simulation/game_simulation.cpp:229`) |

There are still no v3 accounts, credentials, resume tokens, or durable user data. What is new is
**personal data**: a display name derived from a tailnet identity is published to every connected
peer, so v3 discloses something about who is playing that v1 could not. Positions are likewise
disclosed to every peer with full precision — an accepted property of a top-down arena, and a
property any later fog-of-war or spectator feature would have to redesign the snapshot to change.

committed decisions or admission refusals into it. It cannot start, pause, stop, step, or reset the
simulation, and it cannot read world state through the write path. The absence of a lifecycle route
in v3 is structural for the same reason it was in v1.

| Send a command kind the mode does not accept. | Reach a system the mode did not enable; probe for an unfiltered kind. | The boundary checks against `welcome.accepted_command_kinds` and closes `1008 command_kind_rejected`; `InputBatch::create` filters again inside the runtime; the mode is fixed for the process lifetime so the set cannot drift. | Two independent enforcement points, and the advertisement is not one of them. Residual is a mode author registering a kind whose consuming system is missing. |
| Offer `blob-royale.snapshot.v1` on `/api/v3/lobbies/1/session`, or the reverse. | Get v1's permissive one-way semantics on the command route, or command semantics on the read-only route. | Route and subprotocol are validated as a pair; a non-matching offer is `400 PROTOCOL.SUBPROTOCOL_REQUIRED` even when the other route's token is present. | Requires the implementation to select by route rather than by first acceptable offer — the classic way this check is written wrong. Integration test required in both directions. |
| A malicious page in a tailnet user's browser opens a WebSocket to the game and sends thrusts. | Drive a real player's blob from a foreign origin. | Exact `Origin` allowlist, no wildcard, WSS, upgrade bucket, and — new in v3 — `Origin` mandatory on every proxy-forwarded connection including loopback. | **In v1 a cross-site hijack could only read; in v3 it can steer.** WebSocket is not subject to CORS, so `Origin` is the entire browser-side control and it is a header the browser sets, not a proof. One misconfigured allowlist entry is a full write capability. |
| Press Start, resize the lobby, or clear a seat repeatedly while other people are still choosing. | Start a match nobody was ready for; empty a bot somebody just seated; make the lobby unusable. | **None, deliberately.** Anyone in the lobby may send all four lobby commands; the only controls are structural — the four state rules a client renders before the fact (`§ "The lobby commands"`), the phase guard that refuses all four outside `lobby`, and the fact that a lobby never shrinks past an occupied seat. | **Accepted and unmitigated for the supported deployment.** Every peer on the tailnet is an identified person the operator invited, and the worst outcome is a match that starts early or a bot that has to be re-seated. A public deployment must attach an authority to the sender's `ControllerId` above the simulation and refuse an unauthorized lobby command at the sink; nothing on the wire has to change to do it. |
| Send a `seat_npc` naming a bot kind the server does not register. | Get the runtime to construct something it was not asked to, or crash a tick on an unbuildable name. | The kind is checked against the very list the session's own `welcome` published, which is read from the server's controller registry, and a name outside it is `1008 command_payload_invalid`. The simulation never sees an unregistered kind, so no tick can be reached with one. | The list is data rather than a schema enum, so the residual is a registry row whose name is not a publishable `kind_name`. That is refused at startup rather than at the first right-click. |
| One person opens eight sessions from one device. | Occupy eight blobs; dominate a royale match or fill a lobby's seats. | Per-principal session cap of 8, global cap of 32. | **v3 turns a resource limit into a gameplay limit and the numbers were chosen for the former.** Eight blobs per person is a griefing surface with no control at all today; a per-principal *seat* cap of 1 is future work. Under forged forwarded addresses even the 8 does not hold. |
| Join repeatedly to inflate the entity population, or configure a large bot roster and a dense map. | Push the encoded frame past 2,097,152 bytes and trigger the hard invariant failure that stops the process. | 1,024-entity bound with a 2× measured margin; startup validation of statics + zone + roster ceiling; encoder fails closed and never truncates. | The startup validation is the only thing standing between a map/roster configuration change and a remotely reachable process kill. It must be a startup rejection with a named cause, not a comment. |
| Supply a display name containing control bytes, ANSI escapes, or a right-to-left override. | Log injection, terminal escape in `docker logs`, spoofed name in the client. | Printable-ASCII-only grammar validated by exact match; no substitution; structured logging that never logs the received value; the client renders the name as text. | Homoglyph and spacing impersonation inside plain ASCII remains: `Co1e Shaffer` is a legal name. Display names are labels, not identities, and any UI that treats one as an identity is wrong. |
| Send commands continuously across the tick on which the session's entity is destroyed. | Provoke a use-after-free or a double `close_session` in the elimination/disconnect race. | Commands for an absent body are accepted, charged, and discarded; `close_session` is idempotent and called exactly once per session on every path; despawn of an already-absent entity is ignored (`0005-royale-mode.md` § "Roster edge rules"). | This is a lifetime race between the event loop and the simulation worker, and lifetime races are found by TSan and by tests, not by schemas. |
| Read every snapshot as a non-player. | Full positional intelligence on every player and the roster of who is present by name. | None. Reachability is the authorization decision. | Any tailnet peer sees every position and every display name at full precision, forever. This is intended for this game and is an explicit non-property of the protocol. |
| Walk `GET /api/v3/lobbies/<n>/session` across ids and read the `101`/`404`/`409`/`503` each returns, or poll `GET /api/v3/lobbies` and its `session_count`. | A room census -- which rooms exist, which are full, which have failed -- without joining any. | The census is the declared purpose of `GET /api/v3/lobbies`, served to every peer; the parametric route's status oracle reveals nothing the directory does not already list. Grammar `[1-9][0-9]{0,2}` bounds a walk to 999 ids, each spending one HTTP token and, past the fixed segments, one upgrade token. | **No new disclosure, by design.** Occupancy, phase, and health are public to any reachable peer, exactly as every position and display name already are (row above). A public deployment would have to put the directory and the join oracle behind authorization together; neither is a secret on this tailnet. |
| Send `/api/v3/lobbies/01/session` (leading zero), `/1000/session` (4 digits, past the grammar), `/0/session`, `/1/session/` (trailing slash), a percent-encoded `%31`, a query or fragment, or an id above `[lobbies] count`. | Slip the exact matcher into room 1 or another room, or reach a null room and crash a tick. | `[1-9][0-9]{0,2}` rejects a leading zero, `0`, and 4+ digits; the router compares each segment exactly after HTTP parsing, so a trailing slash, a percent substitution, a query, a fragment, or a normalization alias does not select the route (§ "Public surface", inherited from v1 § "Request parsing"); a valid-but-absent id is `404` through `find` returning nullptr. | **This is the classic way a parametric matcher is written wrong** -- prefix-matching, normalizing before comparison, or calling `room()` (which throws) instead of `find()` on an unvalidated id. The router has only ever compared exact paths (ADR 0006 § "The routing model" names this the design's main new risk); every non-room string, on both sides of the segment, needs a test. |
| Poll `GET /api/v3/lobbies` far above the browser's ~1 Hz. | Exhaust the single event loop, or deny the directory to honest pollers, by request volume. | Per-client HTTP bucket (20 burst, 2/s), now per-principal because `trusted_proxy_addresses=127.0.0.1` is set; each poll reads at most 8 already-published snapshots and their atomics under no tick lock, so it never reaches a worker (ADR 0006 § "Backpressure and admission"). | The read is cheap and bucketed, but the bucket is per **principal**, and on the deployed host any local process forges the principal (accepted row above), so the bound is only as strong as that residual. Directory cost scales with room count, capped at 8; measure before non-loopback exposure. |
| Open one session per seat in a room and never send `start_match`, or sit idle in the seats. | Make the room read full (`session_count == seat_count`) to everyone else -- a denial of that whole room. | Per-principal session cap of 8 and global cap of 32 bound how many seats one principal holds; abandonment does not fire while any session is present (`blob_royale_application.cpp:296`). `seat_count` is itself resizable in `lobby` by anyone in the room, which is the accepted lobby-command griefing already listed above. | **Accepted and unmitigated for the supported deployment.** An idle session holding a seat is indistinguishable from a present player; a per-principal *seat* cap of 1 is deferred (§ "Per-principal seat limit of one"), and under a forged principal even the 8 does not bind. A public deployment needs seat-level authority and idle eviction. |
| Repeatedly open sessions into a full pre-match room so each server-issued `join` displaces the lowest-indexed `NpcSeat`'s bot. | Force the reconciliation to retire and rebuild bots, and keep a lobby unstable before Start. | A person displaces a bot only in `lobby`/`countdown`, only the lowest-indexed NPC seat, one seat per admitted session (`apply_join`, `src/simulation/game_simulation.cpp:229`); the seat cap (8/principal) bounds the rate, and a person never displaces another person. | Displacement is the owner's intended rule (a person outranks a bot), but repeated join/leave churns bot sessions -- each rebuilt bot costs a directory entry, a hosted controller, and a `join` (`bot_reconciliation.cpp:101`). **No control, deliberately**, on the tailnet; the only attribution is the `controllers.bot_created`/`bot_retired` log lines, and a forged principal removes the 8. |
| Be the last session in a `running` room and disconnect to trip abandonment, or keep exactly one idle session present so the match can never be abandoned. | Churn a room's bots on every empty, or hold a match open indefinitely between bots nobody can watch leave. | Abandonment is a control-loop decision on `session_count == 0` in `countdown`/`running` (`observe_room_world`, `blob_royale_application.cpp:323`): it retires every bot once and reseats once the room is back in `lobby`, at the 25 ms poll -- one retire/reseat per empty-to-occupied edge, not per frame. A present session legitimately keeps the room live. | Bot churn is bounded to one cycle per abandonment edge and confined to that room's own thread, so it cannot starve another room. Holding a match open with one idle session is the wedge ADR 0006 § "Failure modes" leaves to a match time limit that is not built; **no control for it, deliberately**, on the single-operator tailnet. |
| Open the per-principal maximum of 8 sessions spread across several rooms at once. | Occupy seats in every room simultaneously; distort or deny multiple matches from one device. | The per-principal cap (8) and global cap (32) are unchanged (`server_limits.hpp:28-29`); there is no per-room-per-principal dimension. | **2.4 spreads a cap chosen as a whole-server resource limit across N rooms, where it now reads as a gameplay limit.** Eight seats over four rooms is two per room, enough to sway several matches; under a forged principal the 8 does not hold at all. A per-principal per-room seat cap is future work. |
| From two sessions, land the server-issued `join` for a room's last free seat in the same tick. | Provoke a double-seated roster, an inconsistent count, or a tick crash. | Admission gates `session_count` at `seat_count` before any controller is issued; the tick applies both `join`s in one batch in ascending controller-id order, and `apply_join` seats the first into the last empty seat and finds nothing for the second (`game_simulation.cpp:229`); the loser is closed with the new `lobby_full` reason on `1013` after its welcome and re-reads the directory. | Resolved by batch order, not a lock. Correctness rides on `apply_join` being a no-op for a controller that finds no seat, and on admission and the tick being allowed to disagree for exactly one tick -- which is why `lobby_full` exists. An integration test must pin that the loser is closed and that no seat is filled twice. |
| Upgrade to `GET /api/v3/lobbies/<id>/session` for a room whose runtime threw. | Reach a room with a world nobody trusts, or crash the process by joining a broken runtime. | Admission refuses `503 LOBBY.UNAVAILABLE` before a controller is issued when the room's publication is not ready or its runtime failed (`snapshot_publication.hpp:29` `is_ready()`, set false on failure in `simulation_runtime.cpp`); a failed room's existing sessions close themselves within a presentation period, and the process keeps serving and never resurrects the room (ADR 0006 § "Isolation"). | A failed room stays failed until process restart, by design. **Readiness reads room 1 only**, so a failed room 2..N is invisible to the liveness/readiness probes and shows only as `healthy: false` in the directory; a single room failing repeatedly is a silent partial outage unless the operator watches `runtime.failed` and the directory. |

### Explicitly out of scope

* In-application authentication, accounts, passwords, sessions, resume tokens, and authorization.
* Confidential snapshots, fog of war, spectator restrictions, and anti-cheat beyond server
  authority.
* Client-side prediction, reconciliation, rollback, lag compensation, and general command acknowledgement.
  The narrowly correlated movement-tuning outcome above is not a general acknowledgement bus.
* Matchmaking, persistence, leaderboards, and cross-match identity. Rooms exist since 2.4; nothing
  assigns a client to one, and the directory is the whole of room discovery.
* Internet exposure, Tailscale Funnel, DDoS resistance, WAF behavior, and certificate issuance.
* Snapshot replay, history, deltas, compression, and binary encoding.
* Per-principal seat limits, moderation, kick/ban, and name registration.

These exclusions do not declare the omitted threats harmless. They record that the supported
deployment is one operator's private tailnet, and that widening it requires a new accepted amendment
rather than a configuration change.

| `set_movement_tuning.tuning_request_id` / `.expected_revision` | Safe integers, id positive and revision nonnegative | Correlation and optimistic revision check | Ids increase per controller but never order contenders. |

| `set_thrust.x/y` | finite number `[-1, 1]` | Steering direction | Magnitude clamping is a mode rule, not a wire rule. |
| `set_thrust.input_generation` | optional integer `[1, 2^53-1]` | Captured activation token | Exact optional equality with the entity is required for thrust and zero release. Never retag old held/pending input. |
| `set_seat_count.seat_count` | integer `[1, 64]` | Requested lobby size | A count, not a delta; a shrink past an occupied seat (held by a person, or declared for a bot), or a count above the map's spawn markers, changes nothing. |
| `seat_npc.seat_index` / `clear_seat.seat_index` | integer `[0, 63]` | Which seat | Bounds the value, not the running lobby; an index naming no seat is ignored. |
| `seat_npc.npc_kind` | `controller_kind` | Which bot to declare | MUST be one the welcome published; anything else is `command_payload_invalid`. |
| `seat_npc.profile_name` | optional bounded name | Which configured profile to use | Exact advertised pair required; missing, unknown, mismatched, or null profile is rejected for a profiled kind. |

Schema validation alone cannot prove ascending entity ids, uniqueness, welcome-before-snapshot
ordering, `message_sequence` continuity, strict tick monotonicity, that a published entity's
components agree with the tick that produced them, movement/result coverage by a snapshot,
exact pending tuning correlation, exact encoded byte size, the
data/error exclusivity, that the total entity population fits the frame ceiling, or that a forged
entity id moves nothing. C++ conformance and integration tests MUST cover these normative invariants
in addition to validating schemas.

The snapshot fixture is deliberately a whole world rather than a minimal one: a static wall entity
carrying only `physics_body`, a session-controlled player with `controller_kind: session`, a
`wanderer` bot with identical component structure, and the zone entity carrying only `zone`. The bot
and the player differ in exactly one string, which is the symmetry
`0004-gameplay-architecture.md` § "Controllers" requires. The eliminated entity `5` appears in
`placements` and not in `entities`, which is what a destroyed body looks like. Its `match.seats` is
the same kind of deliberate whole: one of every published seat shape — a person, an NPC whose bot the
server has built, an NPC still waiting for one, and an empty seat — so a decoder can be written
against the example rather than against the prose.

The directory fixture is two rooms. Room 1 is the snapshot fixture's match as the directory lists
it: running since tick `10904`, read at `12904`, a person and a built bot in two of four seats, one
declared bot still waiting, one session. Room 2 is a fresh lobby with one bot declared and nobody in
it. Together they show a listing with every count in use and a listing at the start of its life,
which are the two shapes a client will actually see.

component kind; an entity with zero components; an unordered or duplicated `entity_id`; a

winner; `outcome.kind = none` with a winner; an unregistered `mode_state.schema_id`; an extra member
in a mode-state value; a seat whose `kind` is `empty` carrying a `controller_id`; a `seat_npc`
payload naming an `npc_kind` the welcome did not publish; a `set_seat_count` payload carrying
`seat_count` `0` or `65`; a `start_match` payload carrying any member at all;
`protocol_version` `"3.1"` against the 3.0 schema set; a welcome carrying `lobby_id` `0` or
`seat_count_maximum` `65`; a directory whose ids are not `1..N` in order; a listing whose
`filled_seat_count` exceeds its `seat_count`; a snapshot with
`message_sequence` 1; absent `random_draw_counts`, an absent or unknown stream key, or a count
outside the safe nonnegative integer range; a `set_thrust` payload carrying `entity_id`; a `set_thrust` component outside
`[-1, 1]`; an unknown command kind; a command envelope carrying a version member; a 1,025-byte
inbound message; a command burst above the bucket; `blob-royale.snapshot.v1` offered on
`/api/v3/lobbies/1/session`; a proxy-forwarded connection with absent, repeated, or listed `X-Forwarded-For`;
a direct connection whose forwarding headers are honored; and an encoded frame above 2,097,152
bytes. The encoder never drops an entity and never clamps a value to fit.

## Alternatives considered

### Reuse `/api/v1/snapshots` and add a client message type

Rejected. v1's contract says every client application data frame closes the connection, and clients,
tests, and this repository's own documentation depend on that. Turning a route that promises "your
frames are always invalid" into one that sometimes acts on them is the exact confused-deputy upgrade
v1 § "Explicitly out of scope" forbids without a new surface. A new route and subprotocol make the
capability boundary visible in one grep.

### Let a command name its entity, and check ownership server-side

Rejected. The check is correct exactly as long as every future command kind remembers to perform it,
and the failure is silent and total. Omitting the field makes the server's stamp the only source, so
there is no ownership check to forget. The cost is that one connection can drive only one entity,
which is also the accepted model.

### Add a client sequence number or a command timestamp

Rejected. Neither is needed for correctness — the last command of a kind in a tick wins — and both
are attacker-controlled inputs to ordering. A sequence number invites reorder and replay handling
that would have to be authenticated to mean anything, and a client clock has no place in a
deterministic fixed-step simulation.

Step 10's `tuning_request_id` is the explicit exception for correlation and bounded admission
uniqueness only. It does not order commands, replay requests, or describe a client clock.

### Publish the zone, the alive count, and the placements in `match`

Rejected for the zone and the alive count, accepted for placements. The zone is entity-shaped and is
already a component; publishing it twice gives a client two sources for one circle and a way to
disagree with itself (`0005-royale-mode.md` § "Match section fields"). Alive count is derivable from
the array the client is already iterating. Placements are genuinely not entity-shaped — they
describe entities that no longer exist — so they are a generic `match` field rather than royale mode
state, which is why `royale`'s mode-state block carries neither the zone nor the ranking.

The block's second member, `elimination_grace_ticks`, is the one value there that is mode
configuration rather than observed state, and the argument for publishing it is the counter it
bounds. `zone_exposure.outside_ticks` is already on the wire; without its bound a client can only
report elapsed exposure, which answers a different question than the one a player outside the zone
is asking. The welcome frame was the obvious alternative and was rejected: `welcome-data.schema.json`
is mode-agnostic — it names `mode` and `map` and nothing any mode owns — so a royale balance number
there is a member every future mode inherits and none of them fills. Publishing it per frame also
carries it into a recorded frame, which is where a countdown has to keep working. The cost is that
the wire now exposes a balance number and a change to it is a frame-content change; that is churn
rather than disclosure, and it loses to a player who cannot tell how long they have.

### Make `npc_controller_kinds` a closed schema enum like every other vocabulary

Rejected, and it is the one place this protocol deliberately breaks its own pattern. Every other
closed vocabulary here — component kinds, command kinds, mode-state schema ids — is fixed by this
schema set, and adding a member is a minor version. Doing the same for bot kinds would put a schema
revision, a regenerated client, and a protocol version behind `one row in controller_registry.hpp`,
which is the extension point `0004-gameplay-architecture.md` § "Libraries, and where a new thing
goes" exists to keep cheap. The pattern is kept where it protects a decoder from a value it cannot
interpret; a bot kind is a *label a client offers back to the server*, and a client that has never
heard of `ambusher` renders it correctly by rendering the string. The safety the enum would have
bought is bought instead by the server checking the name against the same list it published, so the
set a client may name and the set the server can build cannot drift.

### Publish the seat roster in the welcome rather than in every snapshot

Rejected. The welcome is sent once, and a lobby is the thing that changes most while a player is
watching it: a seat count, a bot appearing, somebody pressing Start. A welcome-carried roster would
be stale the moment a second person joined and would need an invented push message to correct, which
is a second server message model for one section. Riding the snapshot also carries the lobby into a
recorded frame, which is where a replay of a match has to be able to show who was in it.

### Reuse v1's `error-response.schema.json`

Rejected; see § "Normative language and canonical artifacts".

### A `warn`-and-continue client on an unknown kind

Rejected for the wire contract; see § "Versioning and fail-closed decoding". This is the one place
v3 knowingly narrows an accepted ADR.

### Resume tokens for reconnect

Rejected for 2.0, not rejected permanently. A resume token is a bearer credential, and a bearer
credential needs issuance, expiry, revocation, storage, and a threat model for its theft — none of
which exists here, and all of which would be the first authentication surface in the project. A
reconnect is a new join with a new controller and a new body. The cost is that a dropped connection
loses the current match, which is acceptable for matches measured in minutes. Adding one later is a
protocol amendment, not a configuration change.

### Per-principal seat limit of one

Deferred, not rejected. It is the correct control for the eight-blobs-per-person griefing surface,
but on the deployed configuration the principal is forgeable by any local process, so the limit
would buy less than it appears to. It becomes worth adding at the same time the forged-header
residual is closed.

## Consequences

* **Positive:** One additive route with its own subprotocol leaves every v1 guarantee intact and
  makes "this connection can cause an effect" a property visible in the request line.
* **Positive:** A command that cannot name an entity removes an entire vulnerability class by shape
  rather than by check.
* **Positive:** Components keyed by kind with one closed schema each mean a new component is a new
  file plus one registration line on both ends, and the closed map makes an unknown kind loud.
* **Positive:** `controller_id` as the durable self-identifier survives elimination and match reset,
  which is what makes placements legible to the player they describe.
* **Positive:** Charging the rate token before JSON parsing bounds inbound CPU with the bucket
  rather than with the parser.
* **Negative:** Like the former v2 session, v3 parses attacker-chosen bytes in C++.
* **Mitigation:** Size, UTF-8, token, parse, envelope, kind, payload — in that order, failing closed
  at each step — plus a fuzz corpus for the envelope and sanitizer coverage of the decode path as a
  release gate.
* **Negative:** A loopback trusted proxy lets any local process forge both the accounting principal
  and the display name.
* **Mitigation:** None in-application. It is accepted for a single-operator host and documented here
  and in the readiness checklist as a blocker for any shared host.
* **Negative:** The entity bound drops from v1's 4,096 players to 1,024 entities of all kinds.
* **Mitigation:** The arithmetic is in § "Limits"; 1,024 is 2× headroom under the unchanged frame
  ceiling and far above the deployed session cap. Raising it requires re-measuring the frame, not
  editing a constant.
* **Negative:** Fail-closed decoding means one unknown kind ends a session that could have kept
  rendering.
* **Mitigation:** The version check runs first, so a client fails on the version rather than on a
  surprise mid-match; and minor versions are a deployment event on a single-operator host.
* **Negative:** Reconnect loses the match, and eight sessions from one device is a griefing surface.
* **Mitigation:** Both are recorded as future work with the control named; neither is load-bearing
  on a trusted tailnet.
* **Operational:** The existing trusted-proxy configuration enables per-player accounting and
  carries the accepted local-forgery residual. This source migration does not deploy or change
  proxy authority; deployment evidence remains a separate verification task.
* **Reversibility:** Revert the coordinated server/assets release together if rollback is needed.
  V1 remains a read-only observer, not an automatic fallback for a failed v3 session; the browser
  fails visibly rather than silently losing input or terrain semantics.

## Non-loopback and shared-deployment readiness checklist

Acceptance fixes the protocol-v3 wire and trust-boundary contract. It does not claim that the
deployment, proxy, or operator facts are ready. Before any deployment beyond the accepted
single-operator tailnet, the owner and operator must answer each item with evidence, not inference:

* [ ] `trusted_proxy_addresses` names the proxy exactly, and every operator understands that a
      loopback entry grants forgery of the principal and the display name to every local process.
* [ ] No untrusted user account, container, or service shares the game host with the listener.
* [ ] The proxy strips `X-Forwarded-For`, `Forwarded`, `X-Real-IP`, and every `Tailscale-User-*`
      field arriving from a client, and sets them itself.
* [ ] Route-and-subprotocol pairing is tested in both directions: v1 token on the v3 route and v3
      token on the v1 route both fail.
* [ ] The `Origin` allowlist contains exactly the deployed origin, and the direct-loopback `Origin`
      relaxation is proven unreachable whenever loopback is a trusted proxy.
* [ ] A forged `entity_id` in a command frame is proven to close the connection and move nothing.
* [ ] The command bucket, the 1,024-byte limit, and the pre-parse token charge have deterministic
      integration tests, including the burst boundary.
* [ ] The command decode path is in the fuzz corpus and is covered by the ASan/UBSan lanes.
* [ ] Startup rejects a map, roster, and bot configuration whose published entity population can
      exceed 1,024, with a named cause.
* [ ] The worst-case encoded frame has been measured on native Linux against the real map and
      roster, not only computed.
* [ ] `close_session` is proven to run exactly once on every close path, including abnormal
      transport close during elimination.
* [ ] Display names are proven never to reach a log line, a close reason, or an error body as raw
      bytes, and the client renders them as text.
* [ ] Product and operations documentation says plainly that v3 has no in-application
      authentication, that reachability is the authorization decision, and that every peer sees
      every position and every name.
* [ ] Any future addition of a resume token, a second room, or a non-tailnet ingress is treated as a
      new protocol amendment that defines authentication and ownership together.
